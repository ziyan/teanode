# Live transcription while recording, in speaker bubbles

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It follows `~/.claude/PLAN.md` (the ExecPlan rules); a reader needs only this file and the working tree.

## Purpose / Big Picture

Today a person records a meeting on the iPhone and sees only a clock and a level meter. The words appear after they press Stop, the phone uploads the audio, and the server transcribes it with speaker separation ("diarization": telling apart who spoke when). After this change the recording screen shows the conversation as it happens, as chat bubbles: words appear within a second or two of being spoken, and about half a minute later each bubble is given its speaker, with the account owner's bubbles on the right in the accent color, the same layout as the finished recording. The person can name a speaker on a live bubble; from then on that speaker comes back by name for the rest of the recording. The dashboard's page for a recording that is still being captured shows the same live conversation. Nothing about the durable recording changes: the audio file on the phone is still written exactly as today, and if the network drops the recording continues and the bubbles catch up when the audio is uploaded.

To see it working: start a recording on the iPhone (Recordings tab, microphone button), speak two sentences, and watch them appear as a bubble; have a second person speak and, within about 40 seconds, see the bubbles split into two speakers; long-press a bubble of the second person, choose Name speaker, type a name, and see later bubbles of that person carry the name.

## Decision Log

- Decision: two transcriptions run side by side, a streaming one for instant words and the existing file-based speaker-separated one for speakers and the saved transcript.
  Rationale: the provider's streaming transcription (used by voice mode, `internal/voice/voice.go`) returns words within a second but cannot tell speakers apart; the file-based model `gpt-4o-transcribe-diarize` (`internal/llm/openai_transcription.go`) tells speakers apart and accepts known voice samples but only for a finished file. The saved transcript stays the speaker-separated one, so a recording made offline ends the same way, just without the live view.
  Date/Author: 2026-10-13, Claude, approved by the owner in conversation.
- Decision: cuts between pieces prefer the end of an utterance reported by the streaming transcription, fall back to a pause in the input level, and are forced at 60 seconds; correctness never depends on where the cut falls.
  Rationale: the owner pointed out that background noise or music defeats a loudness-based pause detector. The streaming provider decides utterance ends from speech, not loudness. Even so, a forced cut can split a sentence, so Milestone 2 makes the server re-read the sentence that crossed the cut.
  Date/Author: 2026-10-13, Claude.
- Decision: the sentence that crosses a cut is fixed by holding back the last segment of each piece and transcribing the next piece together with the audio from where that segment started (at most 15 seconds), not by matching repeated words.
  Rationale: replacing one segment is deterministic; fuzzy de-duplication of overlapping words is not.
  Date/Author: 2026-10-13, Claude.
- Decision: live words cost a second transcription; it is on by default and can be turned off in the agent's recording settings.
  Rationale: streaming transcription is billed per minute in addition to the file-based pass; both are cents per hour, and the owner asked for live text.
  Date/Author: 2026-10-13, Claude.

## Context and Orientation

TeaNode is a self-hosted mail and agent server written in Go (`internal/`, entry points in `cmd/teanode-server` and the CLI `cmd/teanode`), a React dashboard (`web/src`), and a SwiftUI iPhone app (`ios/TeaNode/Sources`, shared logic in the Swift package `ios/TeaNodeKit`). The API is GraphQL generated by reflection from Go structs in `internal/api/v1api/apigraph`; the CLI reaches it through `internal/client`; the agent's tools live in `internal/agent/tools`. Read `AGENTS.md` and `CONTRIBUTING.md` first; naming rules there are strict (no abbreviations, `self` receivers, booleans start with is/has/can/should).

A recording (`internal/models/recording.go`, table `recording`) has a capture state (`active`, `paused`, `interrupted`, `stopped`, or `imported`) and a list of media: each media item is one audio file (`recording_media`), placed on the recording's timeline at `timeline_start_ms`. The iPhone's recorder (`ios/TeaNode/Sources/MeetingRecorder.swift`) already writes a recording as a series of media, one file per segment of at most 600 seconds (`record(forDuration: 600)` in `startSegment`), rolling over in `rollover`/`finishSegment`. The uploader (`ios/TeaNode/Sources/RecordingUploads.swift`) uploads media in 8 MiB parts and today only considers recordings whose capture state is `stopped` or `imported`; in `advance` it publishes the capture as `stopped` before uploading. Caution: the segment currently being written is already listed in `localMedia` with `originalSha256 == nil`, so an uploader that ran during capture would hash and upload a file that is still growing; Milestone 5 must skip it.

On the server, a transcript run (`recording_transcript_run`) belongs to one media item. The agent's worker sweep `queueRecordings` (`internal/agent/recording.go`, about every 5 seconds) creates a run for every media that is upload-complete and has none, and enqueues an `AgentJobRecording` job; the job decodes the media to 16 kHz mono PCM in chunks of at most 10 minutes and sends each chunk to the provider as a "transcription attempt" (`recording_transcription_attempt`) that yields segments (`recording_transcript_segment`: speaker label `local_speaker_id`, start and end in timeline milliseconds, text). Capture state is not checked anywhere in this path, so pieces uploaded during capture would already be transcribed. The timeline read `ReadRecordingTranscriptTimelinePage` (`internal/db/database_recording_transcript.go`) takes the latest completed run of each media and pages their segments ordered by start time; it works for an active capture too.

Speakers: a speaker label from the provider is meaningful only inside one attempt ("A" in one piece is not "A" in the next). A person names a speaker with `CorrectRecordingSpeaker` (`internal/db/database_recording_speaker.go`), which stores a correction tied to one attempt and one label and an identity (`recording_speaker_identity`, with `is_account_owner` for the person themselves). After a correction, speaker curation (`internal/agent/recording_speakers.go`, woken immediately by `WakeRecordingSpeakerCuration`) cuts a 2 to 6 second clean clip of that speaker into a voice sample (`recording_voice_reference`). When a later attempt is transcribed, up to four voice samples, one per name, are sent with it (`internal/agent/recording_references.go`), and the provider labels a matched speaker with the sample's name. Since the recognition change on this branch, the projection `ProjectRecordingSpeakerCorrections` (`internal/db/database_recording_speaker_projection.go`) marks such segments `IsRecognizedSpeaker` with the identity's name and owner flag.

Three server behaviors break a live capture and are fixed in Milestone 1. Every `UpdateRecordingCapture` advances the recording's `source_generation` (`internal/db/database_recording.go`), and `CorrectRecordingSpeaker` refuses a stale generation, so the phone's periodic capture updates would make naming a speaker during capture fail. Every completed run starts a memory sync (`SyncRecordingKnowledge`, which re-reads every segment of the recording) and queues the naming job `recording_brief` (a full-transcript model call), which would repeat after every 30-second piece. And curation resets per run.

Voice mode: `internal/voice/voice.go` opens a provider streaming-transcription session (`Open`), takes 24 kHz mono 16-bit PCM (`Append`), and emits `Event`s: words of an utterance as they are heard, and each utterance's final text in spoken order. The dashboard and the phone reach it through a websocket served from `internal/api/v1api/apigraph/agent_voice.go`; the phone's side is `ios/TeaNode/Sources/VoiceCall.swift`. The provider also reports, per utterance, `audio_start_ms` and `audio_end_ms` relative to the start of the session (events `input_audio_buffer.speech_started` and `speech_stopped`); the package does not expose these yet.

## Plan of Work

Milestone 1, the server takes pieces during capture. In `internal/db/database_recording.go`, `UpdateRecordingCapture` keeps its expected-generation check but stops advancing `source_generation` for progress (duration growing, gaps extending, active and paused switching); only the move to `stopped` advances it. Check every test that relies on the bump (search `UpdateRecordingCapture` in `internal/db/*_test.go` and `internal/agent/*_test.go`) and keep the protections they test. In `internal/agent/recording.go`, where a run completes, skip `SyncRecordingKnowledge` and the `recording_brief` queueing while the recording's capture state is not `stopped` or `imported`; when `UpdateRecordingCapture` moves a capture to `stopped`, queue both once (the sync and the existing naming sweep will see a stopped capture with completed runs). Curation keeps running per run, since naming must work live. Acceptance: a DB test creates a capture, updates its progress three times, names a speaker with the generation read before those updates, and the correction succeeds; an agent test completes two runs of an active capture and asserts no `recording_brief` job and no knowledge document exist until the capture is stopped, then exactly one naming job.

Milestone 2, whole sentences across cuts. Add to `recording_transcript_run` a nullable `handoff_start_ms` (migration `0174_recording_live_handoff.sql` with its reverse; read `docs/coding/database-migrations.md`). When the job transcribes media N of a capture and media N-1 has a completed run whose last segment ends within 500 ms of media N-1's end (the speech ran into the cut), the job decodes the audio of media N-1 from that last segment's start (but no more than 15 seconds before the cut) and places it before media N's audio in the first chunk, offsetting timestamps so segments land at their true timeline positions; it records `handoff_start_ms` on media N's run. The timeline read then hides segments of media N-1's run that start at or after the following run's `handoff_start_ms`. The last piece of a stopped capture has no follower, so its last segment stands. Pieces from an import are never handed off. Acceptance: an agent test with the fixture provider transcribes two media where the fixture returns a segment crossing the cut, and the timeline shows the sentence once, whole, at the right time; a second test with no crossing (last segment ends 2 s before the cut) shows no handoff.

Milestone 3, stable speakers and live naming. Add a table `recording_temporary_speaker` (same migration): recording id, a label `Speaker 1`, `Speaker 2`, ... unique per recording, a voice-sample blob id like `recording_voice_reference` has, and the identity id once named. After each run of an active capture completes, for each provider label of that run not recognized as a known identity, the curation step cuts a clean 2 to 6 second clip (reuse `isCleanRecordingVoice` and the clip code in `recording_speakers.go`) and either matches it to an existing temporary speaker of the recording (the provider labeled it with that temporary speaker's label because the sample was sent) or creates the next one. `recording_references.go` sends, within the provider's four, first named identities that appeared in this recording, then the account owner, then the recording's temporary speakers most recently heard; temporary speakers are sent under their `Speaker N` label. The projection maps a segment whose label is a temporary speaker's label to that temporary speaker: the view shows `Speaker N` consistently across pieces. Naming a temporary speaker (a new mutation `NameRecordingTemporarySpeaker(recordingId, label, confirmedName, isAccountOwner)`, with CLI `teanode recording speaker-name-temporary` and the recording tool's operation `temporary-speaker-name`) creates or reuses the identity, writes the ordinary corrections for every attempt where that label appears (so everything downstream, memory included, sees normal corrections), and links the temporary speaker so later pieces are sent the sample under the confirmed name. Temporary speakers and their samples are deleted when the recording is deleted and are never sent for another recording. Acceptance: an agent test with three fixture pieces where the fixture provider returns `Speaker 1` when that sample is sent shows one consistent label across all three; naming it makes all three pieces show the name, and the fourth piece is sent the sample under the name.

Milestone 4, live words through the server. Extend `internal/voice` so `Event` carries `UtteranceStartMS` and `UtteranceEndMS` (session-relative, from the provider's speech started and stopped events). Add a websocket endpoint for a recording's live transcription next to the voice one, authorized like it, which takes a `recordingId` and the timeline millisecond at which the stream starts, opens a voice session with the recording settings (no answer audio), and stores each final utterance in a new table `recording_live_utterance` (recording id, utterance id, start and end in timeline milliseconds, text), and relays word events to the socket. Add `liveUtterances` to the timeline view (`ReadRecordingTranscriptTimeline`): utterances whose time range is not covered by a completed speaker-separated run, so the client draws them as bubbles without a speaker until the run arrives. Live utterances are deleted once the capture is stopped and every media's run is complete, and with the recording. They are never sent to memory. Setting: `agent.recording.isLiveTranscriptionEnabled` (default true) in `internal/config`, shown in the dashboard's agent settings where the recording settings are, and in `teanode settings`. Acceptance: a test drives the endpoint with a fake provider session and reads back the stored utterances in timeline order; the timeline view returns live utterances only where no run covers them.

Milestone 5, the iPhone. In `MeetingRecorder.swift`, replace the 600-second segment with a cut policy: after 20 seconds, cut at the next utterance end reported by the live stream, or, when the stream is not connected, at the first 250 ms where the metered level stays within 6 dB of the lowest level of the last 10 seconds; always cut at 60 seconds. Start an `AVAudioEngine` input tap alongside the `AVAudioRecorder` (the recorder stays the durable writer and is not otherwise changed), convert to 24 kHz mono 16-bit, and send frames to the live socket while connected; reconnect with backoff and never let the stream affect capture. In `RecordingUploads.swift`, allow uploads of a capture that is `active`, `paused` or `interrupted`, but only of media whose `originalSha256` is set (closed segments), publish capture progress with `UpdateRecordingCapture` (state and duration) instead of only `stopped`, and keep removing the local entry only after stop (as on this branch). The recording screen (`RecordingCaptureView.swift`) shows the conversation above the controls using the same bubble view as the detail screen (`RecordingConversationView.swift`), fed by the timeline view every few seconds plus word events from the socket; live utterances without a speaker are drawn as neutral bubbles on the left with no name; long-press offers Name speaker and This is me, calling the temporary-speaker mutation for temporary speakers and the ordinary correction otherwise. Strings in `ios/TeaNode/Resources/Localizable.xcstrings` with English, Simplified Chinese and Japanese; follow `ios/DESIGN.md`; add CI screenshots of the recording screen with live bubbles in light, dark and largest text using the demo server (`DemoServer.swift`), with an assertion in `ios/scripts/assert-recording-screenshot.swift`.

Milestone 6, dashboard and parity, deploy. The dashboard's recording page (`web/src/pages/recordings.tsx`, `web/src/recording/conversationView.tsx`) polls the timeline every 3 seconds while the capture is not stopped and draws live utterances as neutral bubbles; temporary speakers can be named from the bubble menu. CLI `teanode recording timeline` prints live utterances marked as live. Deploy the server before any app build that reads the new fields, then test on a real iPhone: a 10-minute two-person conversation with music in the background, checking that no sentence is cut or repeated, that speakers stay consistent, and that naming applies to the rest of the recording.

## Validation and Acceptance

Each milestone names its tests above; all must fail before and pass after. End to end, on the deployed server and a TestFlight build: words appear on the recording screen within about two seconds of being spoken; speaker labels appear within about 40 seconds; a sentence spoken across a forced 60-second cut (keep talking over music) appears once and whole in the finished transcript; a speaker named at minute two carries the name in every later bubble and in the finished recording; stopping the recording produces the auto title and summary once.

## Idempotence and Recovery

Migrations are additive with reverse files. Live utterances and temporary speakers are derived data and can be deleted at any time without losing the recording; the durable audio path is unchanged, so a failed live stream or a failed piece transcription never loses audio. Re-running a milestone's steps is safe; the sweep only creates runs for media without one.
