# Passwords: logins, passkeys, cards and notes, readable only on the person's devices

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds. It is maintained in accordance with the ExecPlan rules the maintainer keeps outside this repository; everything a contributor needs is written here.

## Purpose / Big Picture

People keep their passwords in a manager (Apple Passwords, Bitwarden, 1Password, or `pass`, the Unix password store). After this plan, TeaNode is that manager, on the person's own server:

- **Passwords** holds logins (user name, password, sites, one-time code secret, passkeys), cards and notes. Everything in it is encrypted on the person's devices before it reaches the server. The server, its operator, a stolen backup and the agent see only encrypted data, except for the items the person lets the agent use.
- The person sets Passwords up once, with a **passphrase** (separate from their TeaNode sign-in) and a **recovery key** they print or save. A device asks for the passphrase once; after that the iPhone opens it with Face ID and Chrome keeps it open for a time the person chooses.
- The **TeaNode Chrome extension** fills logins, offers to save a login after the person signs in, generates passwords, and creates and uses passkeys on websites.
- The **iPhone app** has a Passwords screen and is an **AutoFill provider**: in Settings, General, AutoFill & Passwords the person turns on TeaNode, and Safari, Chrome and other apps offer its logins, passkeys and one-time codes. A passkey sign-in on a computer (the QR code) can use it too.
- The **dashboard** has a Passwords page, and `teanode passwords` does the same from the command line, including importing a `pass` store, and Chrome, Apple Passwords or Bitwarden exports.
- The person can **share** an item with a circle or one person in a circle. The people it reaches can use it (fill, copy, sign in with its passkey); only the owner changes it.
- The person can let **the agent use** one item. The agent then signs in with it in its headless browser or in the person's attached tab: the password, code or passkey is typed in or signed by TeaNode, only on that item's sites, and never shown to the model. A note the agent may use is read by the model.

To see it working at the end: on a development server, set up Passwords on the dashboard with an invented passphrase and save the recovery key. `teanode passwords import pass` on a test store of three invented entries (one with a `login:` line, one with an `otpauth://` line) adds three logins. The Chrome extension, unlocked, fills the login on a local test page served at `https://login.example.test`, offers to save a new one after a test sign-in, and creates then uses a passkey on a local WebAuthn test page. The iPhone simulator (demo data) shows the Passwords screen and the AutoFill list. A second account in the same circle sees a shared login and fills it. Asked "sign in to the test site and read my order", the agent says it may not use that login until the person lets it; after the person turns on "Let the agent use this" on that item, the agent signs in in the headless browser, and its transcript contains no password. A database dump shows no site name, user name or password in plain text.

## Surprises & Discoveries

- Apple lets a third party app be the system's password and passkey provider through an AutoFill Credential Provider extension (`ASCredentialProviderViewController`, entitlement `com.apple.developer.authentication-services.autofill-credential-provider`). Passwords and passkeys since iOS 17, one-time codes and "text to insert" since iOS 18. Safari and Chrome on the iPhone both use it. Up to three providers can be on at once.
- The extension is killed at about 120 MB (this repository's share extension found the same). It must read a local encrypted copy and never run the passphrase derivation; the app keeps the copy current.
- A passkey made by a provider must be a synced one: Apple returns no device-bound keys from a provider. Flags BE and BS set, sign count 0, attestation `none`.
- A provider gets passkey sign-ins from a computer's QR code (hybrid) from the system, with no code of its own.
- Chrome gives extensions no passkey provider API (`chrome.webAuthenticationProxy` is for remote desktop software and suspends the browser's own WebAuthn). Bitwarden, 1Password and Dashlane replace `navigator.credentials.create` and `.get` from a script in the page's own world at `document_start`, relay to the extension, and fall back to the browser on request. This plan does the same.
- A 2025 study (DOM-based extension clickjacking) showed that a page can make a manager's fill menu invisible and trick a click. Defences: the menu in an extension-owned frame, checks that it is visible and on top when clicked, trusted events only, no fill on page load, and exact host matching by default.
- A 2026 USENIX Security paper attacked Bitwarden, LastPass and Dashlane assuming a malicious server; most attacks came through sharing, key handoffs and unauthenticated encryption. Hence: authenticated encryption with the item's id in the associated data, a person's public key shown as a short safety code, and a warning when a recipient's key changes.
- LastPass's breach exposed site addresses kept in plain text. Here site addresses, names and user names are encrypted like the password; a person's list is small enough for a device to decrypt all of it and match sites locally.
- The repository already seals secrets with AES-256-GCM under the server secret (`internal/util/secretbox`), models shares with a user or circle grantee (`health_share`), and ends shares when a person leaves a circle (`endSharesOutsideCircles`). TeaNode's own passkeys use `go-webauthn` as a relying party, which does not help an authenticator; signing is written here.
- WebCrypto has no Argon2, Apple's CryptoKit has neither Argon2 nor (on Linux, where TeaNodeKit is tested) itself. PBKDF2-SHA256 is native on every surface (WebCrypto, CommonCrypto, Go's x/crypto, `swift-crypto`'s `_CryptoExtras` on Linux).

  Rationale: the maintainer chose it ("only on my device is preferred"); the operator of a family server is often one of its people, and passwords are the worst thing it could lose. A misled agent cannot read what the server cannot read.
  Date/Author: 2026-10-20, the maintainer.

  Rationale: the maintainer's choice. Losing both passphrase and recovery key loses Passwords; the only way out is to erase and start again, which the setup screen says.
  Date/Author: 2026-10-20, the maintainer.
- Decision: the agent may use an item only after the person turns on "Let the agent use this" on it. Off for every item by default.
  Rationale: the maintainer's choice, and the maintainer asked that sharing and the agent's headless browser be thought through with end-to-end encryption. The person's device wraps that one item's key for the server's agent key (see below), so the server can open exactly the items the person let it, and nothing else.
  Date/Author: 2026-10-20, the maintainer.
- Decision: the first version has logins (with one-time codes and passkeys), cards and notes.
  Rationale: the maintainer chose cards and notes in the first version.
  Date/Author: 2026-10-20, the maintainer.

  Rationale: the maintainer: "let's drop the card autofill, it's not often used".
  Date/Author: 2026-10-20, the maintainer.
- Decision: a login's secrets never reach the model. The agent fills a password or one-time code, or signs with a passkey, through the browser by the item's id; TeaNode puts the value in, only on a page whose host matches one of the item's sites.
  Rationale: the agent needs to sign in, not to know the password; a page that talks the model into "type the password here" gets nothing on another host.
  Date/Author: 2026-10-20, this plan.
- Decision: the agent can use a granted item in a run the person started: a conversation with them, or a schedule they wrote themselves. A run that content started (an inbound mail, a webhook, a chat app, a goal, a dream, a schedule the agent wrote for itself) cannot list, read or sign in with an item. Each use is recorded on the item ("used by the agent on example.com") and in the audit log.
  Rationale: signing in on a schedule (a monthly statement) is the reason to grant an item, but a run steered by a stranger's mail must not be able to spend a login. The first version allowed every run; the security review of 2026-10-20 narrowed it (`tools.IsStartedByPerson`, `AskRun.IsStartedByPerson`). The attached tab is still only used while the person watches (`20260910-the-attached-tab-is-the-persons.md`).
  Date/Author: 2026-10-20, this plan; narrowed 2026-10-20 after the security review.
- Decision: after a fill, the page is locked per tab and per document, not per tool: the browser tool refuses scripts, pictures, storage, the network log and every DevTools command but input and moving the page on that tab until it commits a new document that is not a move through the history; the network log is turned off and forgotten before the fill; no request body is ever kept; every answer is scrubbed in the forms a page or a log writes a value.
  Rationale: the first version unlocked on any change of address, on switching tabs and on the tool's own navigation, which let `history.pushState` or a second tab lift it, and kept the network events, where a form's request carries the password. The extension reports document commits (`chrome.webNavigation.onCommitted`) in the existing `update` message (protocol stays 5).
  Date/Author: 2026-10-20, the security review.
- Decision: the agent matches the origin of a page to an item's sites, port included: a site that names a port matches only that port, a site that names none matches only the default port of its scheme, and an http page (loopback only) matches only a site saved as http.
  Rationale: a login for `example.com` must not be typed into another service on a port of the same host.
  Date/Author: 2026-10-20, the security review.
- Decision: a card cannot be granted to the agent in the first version.
  Rationale: paying stays the person's act; the payment skills already ask call by call (`20261016-a-payment-skill-is-shared-call-by-call.md`).
  Date/Author: 2026-10-20, this plan.
- Decision: no agent reads an item shared with its person. Only the owner can grant an item to their own agent.
  Rationale: the same rule as Health (`20261018-health-is-shared-by-category-as-day-summaries.md`): the owner decides what reaches a model's provider.
  Date/Author: 2026-10-20, this plan.
- Decision: PBKDF2-SHA256 with 600,000 iterations derives the passphrase key; not Argon2id.
  Rationale: native on every surface (see Surprises); Argon2id would need WebAssembly in the dashboard and extension and a C library in the app. The iteration count is stored with the wrapped key so it can be raised later.
  Date/Author: 2026-10-20, this plan.
- Decision: our own clients, not the Bitwarden API.
  Rationale: Vaultwarden shows the Bitwarden API can be served, but it is large, changes with Bitwarden's clients, and has no circles or agent. Bitwarden's JSON export is imported instead.
  Date/Author: 2026-10-20, this plan.
- Decision: recipients use a shared item; only the owner changes it.
  Rationale: one writer per item keeps the encryption simple (the owner's device rewraps on every change) and matches how location and Health are shared. Letting recipients change it would need a new choice here.
  Date/Author: 2026-10-20, this plan.
- Decision: `ErasePasswords` stays a tap only, with no proof of the passphrase or recovery key, and no confirmation text argument.
  Rationale: erasing is the only way out when both the passphrase and the recovery key are lost, so asking for either as proof would shut the one door that case has. What guards it is the tap (a signed-in session the person approves on the dashboard or in the iPhone app, never a token, so the command line and the agent cannot do it; the command line says where to approve it), the screen that says what is lost before it asks, and the audit entry. An erase takes every item, key and share of that person, and nothing of anybody else's. Adding an argument that the clients must send would only be a convention a replayed call could repeat, so it was left out.
  Date/Author: 2026-10-20, the second review.
- Decision: the agent using an item does not raise the item's revision. It sets `last_used_by_agent_at` and the used-by note and writes the audit entry, and nothing else.
  Rationale: a revision is the number a device saves against ("changed on another device" when it has moved), so an agent use that raised it made a person's open editor fail to save for no change of theirs. The cost is that a device learns the new used-at on its next full read of the item (opening it, or a refresh of the list), not from the changes feed.
  Date/Author: 2026-10-20, the second review.
- Decision: a schedule is the person's only when its recorded writer is exactly "person", and anything the agent changes about one (its prompt, cron line, where it answers, or whether it is on) makes the agent its writer. The person saving a different prompt on the dashboard or the command line makes the person its writer; saving the same prompt again, or switching it off, does not.
  Rationale: the agent could otherwise take a schedule the person wrote, rewrite what it does from something it had read, and have it run with the person's authority, which includes signing in with a granted item. A writer that is empty or unknown is treated as not the person's.
  Date/Author: 2026-10-20, the second review.
- Decision: on a locked tab, `Page.navigate` is sent only with an http or https `url` and no other parameter, `Page.reload` only with `ignoreCache`, the `navigate` action only to an http or https address, and no other DevTools parameter may hold a `javascript:`, `data:` or `vbscript:` address (typed text is not looked at).
  Rationale: a script address or a script to run on load is a way to read a filled field back through the one kind of command the lock lets through.
  Date/Author: 2026-10-20, the second review.
- Decision: while a page is locked, the browser tool also refuses editing commands and shortcuts that copy or move text (key events with `commands`, a control, alt or meta modifier, Insert, Shift with Delete; a mouse move with a button held; the middle button; every drag command; the `press` action with such a key), refuses every CSS `selector` argument and `wait` for a selector (a locked page is acted on by ref), and shows no input's, textarea's or editable region's text in a snapshot or an element name, not only the filled ones.
  Rationale: the third review copied a filled text field with `selectAll` and `copy`, pasted it into an ordinary input and read it from a snapshot, where the exact-value scrubbing no longer matched; and `input[type=password][value^="a"]` answers yes or no when a page mirrors the value into the attribute, 50 probes to a call with `steps`. The lock's rule is "nothing that could read a field back", and these were reads.
  Date/Author: 2026-10-21, the third review.
- Decision: before any headless command that could read the page, the server asks the browser which document the main frame shows now (`Page.getFrameTree`) and locks again if it is one that was filled; with no answer, the command is refused. `back` returns only after the history has moved.
  Rationale: going back restores the filled document from the history's cache before the `Page.frameNavigated` event is handled and the server's history read finishes, so `steps: [back, wait, evaluate]` could land in the gap. Events alone cannot close a gap that is about their own timing.
  Date/Author: 2026-10-21, the third review.
- Decision: a turn that listed the items, read a note or made up a password is private like one that used Health, and the `conversation` tool's `read` shows what the agent said and its tools answered in such a turn as hidden. The filter moved to `internal/agent/tools` (`IsPrivateToolCall`, `PrivateTurns`) so the tool and the filing runs share it.
  Rationale: a later run (a goal, a schedule the agent wrote, a run a mail steered) could read a note's text or a generated password out of the person's main chat with `conversation read`; and the names, sites and user names of the items should not reach memory either.
  Date/Author: 2026-10-21, the third review.
- Decision: the computer program refuses to read, write, copy, move or edit `passwords-unlock-*.json` and `passwords-keys-*.json` through its filesystem tool and leaves them out of `grep`, sets `TEANODE_AGENT_COMMAND=1` on every shell command and terminal session it starts for the agent, and the `teanode passwords` commands refuse to open the keys, read or write the unlock file or ask for the passphrase when it is set. The names and the mark are in `internal/passwords/localfiles.go`.
  Rationale: `unlock` leaves the account key and private key in the clear for up to 8 hours, and the agent's shell runs as the person, so `teanode passwords show --reveal` or `export` would return every item whatever "Let the agent use this" says. This is defense in depth that stops the obvious routes. It is not a boundary: a program the agent runs can clear the mark or read the file as the person, which the docs say plainly.
  Date/Author: 2026-10-21, the third review.
- Decision: the schedules the daily brief and asset estimate switches write are recorded as written by `built_in`, which is handed to the run as the person's words but does not count as the person starting the run for Passwords; a schedule from before this, with the built-in name and prompt, is treated the same way. The surface `mcp` no longer counts as the person typing.
  Rationale: the brief reads the inbox and the estimates read the web, so mail or a page could steer a run that was allowed to read a note or sign in; an MCP client is another program. Recording a third writer leaves what else these schedules can do unchanged.
  Date/Author: 2026-10-21, the third review.
- Decision: a site and a page with an unreadable port (zero) do not match each other.
  Rationale: `IsOriginOfSites` compared two zeros as equal.
  Date/Author: 2026-10-21, the third review.
- Decision: a private turn (`tools.PrivateTurns`) is replaced by `[hidden: from a turn that used Health or Passwords]` in the history of any run the person did not start, and in the part of the history a compaction summarizes, so the compaction note and the runs that hold each chunk's prompt never contain it. A card keeps whether the turn that raised it was the person's (`agent_interaction.is_started_by_person`, added to migration 0251, false for older rows) and the turn that carries on its answer is the person's only if that was. A message is steered into a running turn only if it is itself one the person wrote. A schedule saved from anything but a tap is written by the agent. The conversation search, `search_everything` and the command line's search leave private turns out in SQL (`SearchAgentConversations`, which now takes `isPrivateIncluded`, true only for a tap), using `internal/agent/privateturn`, the package the tool kit's filter now delegates to. The filing runs judge a turn by the whole conversation, not by the window after their mark. The phone's lock-screen body for the answer of a private turn is "Your answer is ready".
  Rationale: the audit of 2026-10-21 showed a note read in the person's chat could be reached by a compaction summary, by any later background, chat app or resumed run in the same conversation, by an MCP message steered into the person's turn, and one letter at a time by the search. A run the person starts keeps the whole history, so they can go on talking about the note they just read.
  Date/Author: 2026-10-21, the fourth review.

- Decision: the version `SavePasswordItem` (and `RekeyPasswordItem`) replaces is kept only if the item has no kept version younger than an hour; versions are kept 30 days, at most 60 an item, and past that the one just before the newest is dropped, never the oldest. A person's items that are not deleted may hold at most 64 MiB of sealed text (`models.PasswordsBytesMost`), checked in save, re-key and restore. Making the lock time longer needs a tap. A refused save draws no revision number. Writes to Passwords are limited for each person (5000 in a row, 5000 an hour given back), apart for taps and for other credentials, and so are unlock tries.
  Rationale: the audit found that 21 saves of shape-valid garbage from a token pushed the original out of a 20-version history, an erase without the tap; that one person could store about 10 GB and make one list allocate 871 MB; that a token could leave devices unlocked for a week; that refused saves used up the revision counter everybody shares; and that 10 wrong proofs from a stolen token locked the person out of their own dashboard.
  Date/Author: 2026-10-21, the fourth review, server round.
- Decision: `RekeyPasswordItem` (operation 18) replaces an item's fields and item key, deletes every key sealed for a recipient and stores the given ones (each for a recipient a share reaches now, sealed for their current public key), and keeps, replaces or ends the agent's copy but never begins it. It needs no tap.
  Rationale: turning the agent off or removing a recipient used to leave the item key unchanged, so a copy of the old sealed key (a database copy with the server's secret, or a removed recipient) opened every later version of the item.
  Date/Author: 2026-10-21, the fourth review, server round.
- Decision: a page the agent ran script in is not filled (amended below: the mark is the whole site's), and a tab the agent signed in to has its cookies and storage kept from it. The document an `evaluate`, a `cdp` method that is not on a short list of read-only ones, or a `javascript:` or `data:` address ran in is marked (per tab and document, ended by a new document the way the lock is, exact by loader id in the headless browser); `fill_login`, `fill_one_time_code` and `passkey_sign_in` are refused on it for both targets. A tab that ever got `Page.addScriptToEvaluateOnNewDocument`, `Runtime.addBinding`, `Debugger.*`, `Fetch.*` or request interception is never filled again. The headless fill also refuses a form that sends to another host or port than the page (the extension's `isFormSendingElsewhere`, ported). Once a password or code is filled into a host in a tab, the `storage` action for that host and the `cdp` methods that return cookies, storage or network events (`Network.getCookies`, `Network.getAllCookies`, `Network.enable`, `Storage.*`, `DOMStorage.*`, `IndexedDB.*`, `CacheStorage.*`, `Fetch.*`) are refused for the rest of the tab's life.
  Rationale: the audit scripted a page first (an input listener that beaconed the value, or `form.action` pointed at another host), then filled, then clicked, which the lock and the host check cannot see because they look at the page after the fill; it also read `document.cookie`, `storage` and `Network.getAllCookies` after a sign-in. `evaluate` stays allowed once the lock lifts, so `document.cookie` and `localStorage` of a signed-in page remain readable by script (an `HttpOnly` cookie is not); `docs/subsystems/passwords.md` says so.
  Date/Author: 2026-10-21, the fifth review, browser round.

- Decision: a site the agent ran script on is never filled again in that browser, not only the document the script ran in. The mark is made before and after each script (so a page replaced while the script was on its way is marked) and is the site's: scheme, host without `www.`, and port. The headless browser clears it with the action `reset`, which throws the browser context away and opens a fresh one. In the person's browser the extension keeps the sites (`scriptedOrigins` in `chrome.storage.local`, origins only), refuses the fills itself, and the options page's "Allow the agent to fill on these sites again" clears them. The server keeps no copy of that list to decide on, because a copy goes stale when the person allows a site again.
  Rationale: the audit scripted a page, then filled it, with a real Chrome: the page was replaced while a script was on its way, so the mark sat on the old document (14 leaks in 25 runs), and a window the script opened stays alive after its document and reads the sign-in page through `opener.document`. What a script leaves behind outlives its page.
  Date/Author: 2026-10-21, the third audit round.
- Decision: the extension offers and fills nothing in a tab the agent is driving. For 60 seconds after the agent's last command in a tab, the extension answers a page's request for a suggestion, a fill, a code, a generated password, a captured login or a save as if there were nothing to offer, unless the person holds the tab and their input is newer than the agent's command and under 10 seconds old.
  Rationale: the agent's real input looks to a page like the person's. It could click a field, open the suggestion frame, click a row and read the fill back with `Runtime.evaluate`, which is an item the agent may not use (proved in Chrome 154: with the check off two clicks filled the field and the script read the password back; with it on both were empty).
  Date/Author: 2026-10-21, the fifth security audit round.
- Decision: the server marks an item `needsNewKey` in the same transaction as anything that narrows access, and only `RekeyPasswordItem` clears the mark; every share key names the item key it was sealed from (`itemKey`), and a key row a tap stored is never overwritten except by a re-key. Devices read the server's mark and act on it, but no device cuts the record on the server's word.
  Rationale: the first version's "needs a new key" marks were kept on one device and never reached the person's others, and a key sealed from an old item key by a device that had not yet seen another device's re-key would have given the old key to someone the new one excludes.
  Date/Author: 2026-10-21, the second and fifth security audit rounds.
- Decision: the access record inside the sealed fields (grantees and whether the agent may use the item) is what a device trusts about who may have an item, not the server's list of shares or its "usable by the agent" flag. It is signed (version and HMAC under a key derived from the account key), each device remembers the highest version it has seen for each item, and an unverified or replayed record gets no automatic action and the person is asked to set sharing again.
  Rationale: the second audit showed a device still trusted the server's word for the flag, the list of shares and (through a forged share) who was waiting. Sealing the record fixed that for the server, but anyone holding an item key (a recipient, or the server through the agent key) could still seal a wider one, and a server could show an old record again; the signature and the remembered version close both. The server's agent opener cannot check the signature (it has no account key), so the protection is that owners' devices never make an agent copy from a record they cannot verify.
  Date/Author: 2026-10-21, the second and fifth security audit rounds.
- Decision: automatic re-keys never widen. A re-key the person did not start seals only for people in the verified record who already had a key when it last saw the item, and for the agent only if the record says so and it already had a copy; there is a cooldown of 10 minutes for an item and a cap of 20 automatic re-keys for a session. A re-key the person asks for seals for everyone the record reaches.
  Rationale: without the rule a server that sets `needsNewKey` on an item could make a device spread an item key to everybody the record reaches, or keep a device sealing for ever.
  Date/Author: 2026-10-21, the fifth security audit round.
- Decision: the safety code is computed from the public key alone and has eight groups of four digits (about 106 bits), and every surface shows the person's own code (dashboard and iPhone settings, `teanode passwords code`) to be read to the other person and compared against their screen. The wording is "Ask <name> to open Passwords settings on their own device and read you their safety code. Confirm only if it matches." The command line never prints the code it expected on a mismatch.
  Rationale: the first code had five groups (about 66 bits), and nobody could read their own to compare. An intermediate version bound the code to the user id, but the server supplies the user id, so a server that chose both would make a match a birthday search (about 2^53); the key alone needs a search for a key with a given hash (about 2^106 key generations).
  Date/Author: 2026-10-21, the second and fifth security audit rounds.
- Decision: two byte allowances, checked apart. Items that are not deleted hold at most 64 MiB, which is the only thing that stops a save. Deleted items and the versions saves replaced hold at most 128 MiB; when that is full only a change that is not the person's tap is refused, and a tap's save, delete or restore goes ahead. `PurgePasswordItem` (delete forever, a tap only) empties Recently deleted and is the only way to free that allowance before the 30 days are up. One `ListPasswordItems` runs for a person at a time, and its place is held until the answer is written. Write and unlock limits have separate buckets for the person's taps and for every other credential. Revisions are `Int64`.
  Rationale: with one cap a token could fill it with deleted junk and leave the person unable to save, and with none a person could hold much more than 64 MiB for 30 days by deleting and saving again. A tap always going ahead means a stolen token cannot lock the person out of their own Passwords.
  Date/Author: 2026-10-21, the fifth security audit round.
- Decision: a turn whose subagent listed items, read a note or made up a password is private like one that did so itself, and `list`, `read_note` and `generate` are refused in a subagent. A schedule is taken over by the person only by a tap's save that includes its prompt.
  Rationale: a subagent's answer comes back to its parent as a tool result that filing into memory cannot tell from any other; and saving a schedule without changing it must not hand the person's authority to a prompt the agent wrote.
  Date/Author: 2026-10-21, the fifth security audit round.
- Decision: trust the first key and accept a changed one with a notice; comparing codes is optional.
  Rationale: the person judged that nobody compares codes before sharing and anyone asked would press yes, so a prompt is not protection; the signed access record still keeps the server from adding people. Each device keeps one known key for each person (the first it saw), seals for it with no dialog, and accepts a changed key with a notice that stays until dismissed and offers Compare codes. Comparing marks the key "Codes compared" for display only. This replaces the earlier split between confirmed keys (compared by the person, the only ones sealed for) and seen keys (kept to open an owner's items).
  Date/Author: 2026-10-21, the person.

## Follow-ups

- The iPhone app's tap mark rests on a private-use return address (`com.teanode.app:/oauth`) that another app on the same phone can also claim, so an approval the person did not start could hand a tap-level token to that app. The consent page says to approve only a sign-in just started in the app. The fix is a return address only the app can receive (an HTTPS callback tied to the app's associated domain, or App Attest on the sign-in), in the iPhone app and the server together.
- Ports and the address parser in TeaNodeKit. The agent's sign-in (`passwords.IsOriginOfSites`) and the extension (`doesSiteMatchPage` in `web/extension/src/passwords/hosts.ts`) now match the origin, port included, read the same way (an address with a scheme by the browser's parser, a bare host as if it began with `https://`, a backslash or control character refused), and `internal/passwords/testdata/sitematch.json` holds the cases both run. `PasswordsSiteMatch` in TeaNodeKit reads the same file in its tests and matches page addresses the same way; a domain AutoFill hands over (QuickType, an app) has no port or scheme, so it is still matched by host.
- Saved sites with a percent-encoded, international or fullwidth host: the extension reads a site with the browser's parser, which turns them into the plain or punycode host, while `IsOriginOfSites` in Go and `PasswordsSiteMatch` take the text as written. Only sites the person saved are affected, and only so that the extension matches where the others do not; `sitematch.json` should pick one reading and hold the cases.
- The extension keeps the old password of an updated login only as the server's own version (30 days, at most one an hour and 60 in all, plus up to 20 the person saved). The person lists and restores them with `ListPasswordItemVersions` and `RestorePasswordItemVersion` (a tap only), so the bar can say "The old password is kept for 30 days." once the extension offers it: the extension's token is not a tap, so it cannot, and the person does it on the dashboard or in the iPhone app.
- `relyingParty.ts` tells a public suffix from a registrable domain with the public suffix list, private section included, through `tldts` (a pinned dependency). The list is as new as the pinned version, so a hosting service added to it later is refused only after the dependency is updated.
- A passkey the extension makes is user verified only within a minute of typing the passphrase. A faster way to verify (the browser's own prompt, a device PIN) has no extension API.
- A turn resumed from an approved card counts as started by the person only if the run that raised the card was one the person started (the card keeps that) and the answer was the person's own tap (`ResumeSettings.IsAnswerFromPersonsTap`, from `Principal.IsPersonsTap`). A token's answer resumes the run but not as the person's, so it may not use Passwords. Even a tap's answer starts the resumed turn again with nothing in it marked as content that came from elsewhere, so a tool result read earlier in that turn can steer what follows once the card is approved. Narrowing it means marking, per tool call, whether the turn had read untrusted content before the card.
- The `surface` string a client sends (drawer, extension, ios, cli, api and so on) is still only the client's claim, but `AskRun.IsStartedByPerson` no longer trusts it alone: the server carries into the run whether the request was the person's tap (`Principal.IsPersonsTap`) and whether an operator acted as the person (`AskSettings.IsPersonsTap`, `IsOperatorActingAsPerson`), and a surface a person types into counts only with a tap and no operator. A command line token, an app password, an OAuth grant of an app other than the TeaNode app, the extension's token and a program that speaks MCP therefore never start a run that may use Passwords, whatever surface they name. What is left unchecked: a card answered while its run is still live. The answer (`ResolveAgentConfirmation`) is not checked for a tap there, so a token that answers a card raised in a run the person started, while that run is still going, lets that run go on as the person's. Whether a live run can be made to use Passwords that way has not been tested.
- The agent's key cannot be rotated. It is derived from the server secret, so if `server.secret` changes, every item granted to the agent stops opening: the agent's use fails with "cannot be opened", the item stays intact for the person, and nothing is lost until the person turns "Let the agent use this" off and on again from a device, which wraps the item key for the new agent key. There is no tool that does it for them all at once, and no rotation of the key while keeping the old grants.
- Paging for `ListPasswordItems`. It answers every item changed since the revision, each up to 512 KB, so a first read of a full account is one large response and one large allocation: up to 64 MiB of items, and the deleted items with their fields, which can add up to 128 MiB more. The byte caps and the one-listing-at-a-time rule bound it; a page size with the revision as the cursor would keep each response small.
- Replacing the passphrase or the recovery key does not rotate the account key: each only seals the same account key again. Anyone with an older database copy and the old passphrase or recovery key can open the account key and, with the current items, everything saved since. Rotating it means sealing every item key and the private key under a new account key in one change.
- The agent recording that it used an item (`RecordPasswordItemAgentUse`, in the agent's tools) is outside the GraphQL path and is not counted by the write limit. It writes one audit row and one timestamp.
- A person who loses `passwords:use` while others hold keys for their items, or while they hold keys for others' items, does not have those keys removed: they stay until the next re-key of the item, and the reach query leaves the pair out while the role is gone, so nothing is listed or opened for them meanwhile (the listing and the waiting list both use that query). Nothing hooks the loss of the role to delete the keys and raise the items' `needsNewKey`, which the contract asked for; a person who gets the role back has the keys they had before the loss.
- A key row stored by a token fills a waiting recipient's place with whatever it holds, and the owner's devices see the recipient as having a key (`hasKey`), so they do not know to replace it. A later tap's `AddPasswordShareKeys` or `SetPasswordItemShares` replaces it, and so does a re-key, but a tap's row is never overwritten, and nothing makes a device replace a token's row on its own. Showing a recipient whose only key was stored by a token as still waiting would, with the command line sealing keys with a token, keep it waiting for ever.
- The audit row of an agent sign-in names the host, so whoever may read the audit log sees which sites the agent used a person's items on. Hashing the host would hide it from an operator but also from the person.
- `Network.enable` is refused on a tab the agent signed in to, so the person's own debugging of that tab through the agent (watching the requests after a sign-in) is closed. A way to enable the log with the `Cookie` and `Set-Cookie` headers removed would bring it back.
- The agent can still read a session kept in `localStorage`, `sessionStorage` or a cookie without `HttpOnly` with a script after the lock lifts. Closing that needs `evaluate` refused on a signed-in tab for good, which the agent's use of a signed-in page depends on today.
- Schedules from before a writer was recorded count as the person's for Passwords. Migration 0060 gave every older schedule `person`, and a schedule saved with no writer defaults to `person` (`CreateAgentSchedule`), so an agent-written schedule from before the writer existed can use Passwords in its runs. Only the built-in ones are recognized by name and prompt (`isBuiltInSchedule`). Treating the old rows as not the person's would stop the person's own monthly sign-ins from before; a one-time prompt asking the person to confirm their schedules would fix both.
- A private turn made before private turns were filtered is still in the stored compaction notes (`compaction` rows) and run transcripts that earlier compactions wrote, which the conversation tool's `read` shows. New ones are written from the history with the marker.
- A terminal the person attached is not marked as the agent's (it is theirs), and the agent can type into it with the terminal tool. A command typed there runs unmarked.
- The agent's coding agents and the herdr panes it drives start their own shells, which carry `TEANODE_AGENT_COMMAND` only when started through the computer program's shell or sessions.
- An owner's list is bounded by pairs of an item and a person only when the owner changes shares (`models.PasswordSharePairsMost`, 50000, counted as the circle's members without looking at who may use Passwords). A circle that grows afterwards, by people the owner does not control, adds pairs with no change of shares, so the owner's list can still pass the bound until the owner narrows; nothing refuses a person joining a circle because of what its members' owners have shared. The count is a little high on purpose (it also counts members who cannot use Passwords).
- What others share with a person (`models.PasswordsSharedBytesMost`, 64 MiB in all, `models.PasswordsSharedBytesFromOneOwnerMost`, 8 MiB from any one owner, and `models.PasswordsSharedItemsMost`, 20,000 items) is checked when a key is stored and again when the person's list is built, the keys stored first first (the list checks the total and the count, not the 8 MiB from one owner, which a refused growth keeps true), and `models.PasswordsSharedItemsFromOneOwnerMost`, 5,000 items from any one owner, is checked when a key is stored (so one member cannot push 20,000 tiny items at someone). A key is refused for a recipient who is over any of them and the recipient shows `hasTooMuchShared`; `ListWaitingPasswordShares` leaves such a recipient out (so a device does not try again on every pass) and the owner's devices show "<name> has too much shared with them." A key replaces a stored row only if it is no longer than the row, and share keys and agent copies must be in the one canonical text every client writes (232 bytes, at most 400), so a padded key cannot get past the byte bounds. The bound counts every key row stored for the person, including one sealed for a public key they no longer have, until an owner replaces it.
- A save or re-key that makes a shared item larger is refused when a person who holds a key for it would go past the total or the 8 MiB from its owner ("<name> has too much shared with them: make this item smaller or stop sharing it with them"). The owner's device gets that refusal for the first person over, not a list of everyone; a person who is over because of other owners' items blocks the growth until the owner stops sharing with them. The check counts keys stored for a public key the person no longer has too, as the bound does.
- A person keeps at most `models.PasswordRowsMost` (40,000) items counting deleted ones, so a program that saves and deletes cannot make a first read grow without bound; a new item at that count is refused (`ErrLimitReached`) for a tap too, and the person makes room with delete forever. A save that is not a tap stops making new items at `models.PasswordRowsForProgramsMost` (36,000), so the last 4,000 places are the person's. Deleted items otherwise leave after 30 days. Every list query names its items with one array parameter (`= ANY(...)`), because PostgreSQL takes 65,535 parameters in a statement and a list of 70,000 rows used to fail.
- The owner's list is linear in shares and reached pairs now (the shares are indexed by id), but 48,000 shares still take about 0.9 s on a development machine, most of it the reach query (`passwordReachSQL`) checking each pair's circle and role, while the shared revision lock is held. A materialized table of who an item reaches would cut it; nothing needs that yet.
- `ListWaitingPasswordShares` shares the listing place of `ListPasswordItems` (one at a time for a person's taps and one for every other credential), but the document rule in `graph_work.go` that allows one `ListPasswordItems` per request does not count it, so a request that names both gets the second refused with "try again" instead of being refused at once.
- Known keys are per device. A key one device recorded is not carried to the person's other devices, so each records the first key it sees, and a person whose key changed shows the notice on each device separately.

- The dashboard is code the server delivers: a server operator who changes it could capture the passphrase typed there. The iPhone app, the command line and the extension do not load their code from the server (see `docs/subsystems/passwords.md`).
- A document may name at most 25 Passwords mutations (`passwordsMutationsPerDocumentMost`), a change waits at most 5 seconds in all for its locks (`passwordsLockTimeout`: one deadline for the circle membership lock, the revision lock and the row locks, `lock_timeout` set to what is left before each wait; then `ErrPasswordsBusy`, "Passwords is busy with other changes."), and `ListWaitingPasswordShares` reads at most 10 batches of candidates while it looks for pairs that can be given a key. The lock wait also covers the circle code that takes the revision lock to end shares: a person leaving a circle (or a circle or an account being deleted) while Passwords holds the locks for more than 5 seconds is told Passwords is busy, in the same sentence, and tries again; the whole change is under a savepoint, so the member is still in, the account is still there, its photo objects are not deleted (that cleanup is registered only once the deletion succeeded) and `lock_timeout` is put back. A person with no items, shares or keys in Passwords has nothing to end, so leaving a circle for them takes no revision lock and never waits. Deleting an account ends its Passwords shares and keys the way leaving every circle does (`DeleteUser` calls `endPasswordSharesOutsideCircles` after `releaseCircles`), flags the items other people shared with it as needing a new key and gives them a new revision, so the owners' devices re-key. Every change that takes the locks runs under a savepoint (`withPasswordsSavepoint`), so a timed-out wait leaves the request's transaction able to commit and the answer is the busy sentence and not a failed commit. After one change of a document timed out, the rest of that document's Passwords changes are refused at once with the same sentence, so a document of 25 changes waits once, not 25 times.
- The one-hour spacing of kept versions is not applied to a restore, which always keeps what it replaces; a person who restores many times in a row fills the versions of that item (60 and 20 at most) with what they replaced.

## Outcomes & Retrospective

Every surface ships in one pull request: the server, the dashboard, the command line, the Chrome extension, the iPhone app and its AutoFill provider, and the agent's sign-in. The audits changed the design in three places a first version got wrong: a key a device saw once is not proof of who holds it, but the person judged a prompt about it no protection, so devices trust the first key and show a notice when it changes (see the Decision Log); what the server says about who may have an item (its shares, the agent flag) is checked against a record the owner's devices seal into the item, sign and number so that neither a recipient nor the server can widen or replay it; and narrowing access gives the item a new key, which a re-key the person did not start can never use to widen access. The server also bounds how much a token can store and how fast, in two allowances that a tap always gets through. A script the agent runs on a site ends its right to fill there, since what a script leaves behind outlives its page.

## The contract every surface shares

### Encryption (`internal/passwords/` in Go, `web/src/passwords/crypto.ts`, `ios/TeaNodeKit/Sources/TeaNodeKit/PasswordsCrypto.swift`)

All three implement this format byte for byte and are pinned by one file of test vectors, `internal/passwords/testdata/vectors.json`, written by a Go test (`go test ./internal/passwords -run TestWriteVectors -update`) and read by the Go, dashboard (vitest) and TeaNodeKit tests. Every function that draws randomness takes it as a parameter in the code the tests reach (a nonce, a key, an ephemeral private key), so the vectors are deterministic.

- **Text to bytes.** Every string is UTF-8. The passphrase is normalized to Unicode NFC first (Go `golang.org/x/text/unicode/norm`, JavaScript `normalize('NFC')`, Swift `precomposedStringWithCanonicalMapping`). Base64 is standard with padding (RFC 4648 section 4).
- **Sealed value.** AES-256-GCM, a 12 byte random nonce, the 16 byte tag appended to the ciphertext, and associated data given as text. Written as the JSON object `{"version":1,"nonce":"<base64>","ciphertext":"<base64 of ciphertext and tag>"}`. A sealed value is stored in a `text` column as that JSON.
- **Account key.** 32 random bytes.
- **Passphrase key.** PBKDF2-HMAC-SHA256(NFC passphrase, salt of 16 random bytes, 600000 iterations, 32 bytes). The salt and count are stored.
- **Wrap and proof keys.** From a 32 byte secret (the passphrase key, or the recovery key's bytes): `wrap = HKDF-SHA256(ikm: secret, salt: empty, info: "teanode passwords wrap v1", 32 bytes)` and `proof = HKDF-SHA256(ikm: secret, salt: empty, info: "teanode passwords proof v1", 32 bytes)`. The proof is sent as base64; the server stores base64 of SHA-256(proof bytes) and compares in constant time.
- **Account key wrapped.** Sealed with `wrap`, associated data `account-key`.
- **Recovery key.** 32 random bytes, written as RFC 4648 base32 without padding (52 upper case letters and digits 2 to 7) in 13 groups of 4 joined by single spaces. Read back ignoring ASCII spaces, tabs, line breaks and hyphens and the case of A to Z. Anything else is refused, in every client: a padding sign `=`, a letter some languages change when they upper-case it (a sharp s becomes SS, a long s becomes S), a non-breaking space, and a last letter whose unused bits are not zero. `testdata/vectors.json` lists the texts every client must accept (`recoveryKey.acceptedTexts`) and refuse (`recoveryKeyInvalid`).
- **Person key pair.** P-256 ECDH. The public key is the 65 byte uncompressed point (`04 || X || Y`) in base64. The private key is the 32 byte scalar, sealed with the account key, associated data `private-key`. (WebCrypto imports it as a JWK built from the scalar and the public point.)
- **Safety code.** SHA-256 of the label `teanode passwords safety code v2`, a zero byte and the 65 public key bytes; the first 16 bytes taken as eight big-endian 16 bit numbers, each modulo 10000, written as four digits with leading zeros, joined by spaces: eight groups, 32 digits, about 106 bits (`0412 9930 0007 5121 8800 3341 0562 7719`). Only the key goes in: a user id or anything else the server supplies would let a server that chooses both make a match a birthday search (about 2^53) instead of a search for a key whose hash matches a fixed code (about 2^106 key generations). Every surface shows the person's own code, worked out from the key pair the device opened when it unlocked and never from what the server reports (the dashboard's and the iPhone's Passwords settings, `teanode passwords code`), and two people compare by each reading their own off their own screen.
- **Item key.** 32 random bytes per item. Sealed for the owner with the account key, associated data `item-key:<item id>`.
- **Item fields.** The fields JSON (below) sealed with the item key, associated data `item:<item id>:<item kind>`.
- **Sealed for a key pair** (a recipient, or the server's agent key), sent by the item's owner. Make an ephemeral P-256 key pair; `ephemeralShared` = the 32 byte X coordinate of ECDH(ephemeral private, recipient public) and `ownerShared` = the X coordinate of ECDH(owner's person private key, recipient public); `key = HKDF-SHA256(ikm: ephemeralShared || ownerShared, salt: the recipient's 65 public key bytes, info: "teanode passwords share v1", 32 bytes)`; seal the item key with it, associated data `share:<item id>:<owner id>:<recipient id>`, where the recipient id is the recipient's user id, or `agent` for the server's agent key. The recipient computes the same two secrets from its private key, the ephemeral public key and the owner's public key, so only a holder of the owner's private key can make a share that opens: the server cannot plant an item "shared by" somebody. Written as `{"version":1,"ephemeralPublicKey":"<base64 65 bytes>","nonce":"<base64>","ciphertext":"<base64>"}`.
- **Known keys: trust on first use.** Each device keeps one known public key for each other person, by user id: the first key it saw for them, from any source (sharing with them, an item they shared, a waiting share), recorded for an item owner only after an item from them opened with it. The server is never trusted to change one silently, and nobody is asked about one: no surface has a confirm prompt. A device seals an item key for a known or first-seen key at once (sharing with somebody whose key it has never seen seals for the key the server gives and records it). A known key that changes is accepted, sealed for and used to open that person's items, recorded, and shown as a notice that stays until dismissed ("<name>'s key changed. This happens when they erase Passwords and set it up again. If you did not expect it, compare safety codes with them.") with a Compare codes action that shows the old, new and own codes; nothing waits on it. Comparing marks the key "Codes compared" for display only, and `teanode passwords trust <user> <code>` is the optional command line way to do it. Known keys are per device (a person has one key for all their devices, so only erasing and setting up again changes it), and survive both a server that answers with another setup and a sign-out the server ends; they go only when the person removes the account from that device. A device seeing an item for the first time does nothing automatic with it: the person's own action finishes sharing it, trusting the newest signed record the server shows. A recipient who has not set up Passwords has no key and waits; waiting shares complete on every device as soon as the recipient has one. Changing who an item is shared with sends keys for newly reached recipients the signed record reaches; narrowing it, or turning the agent off, gives the item a new key (`RekeyPasswordItem`) sealed again for whoever keeps access, so an old copy of the key opens nothing saved later.
- **Access record.** Every item's fields JSON has an `access` key: `{"isUsableByAgent": false, "grantees": [{"userId": "..."}, {"circleId": "..."}], "recordVersion": 3, "recordMac": "<base64>"}`. Only the owner's devices write it, and they seal it again with the fields whenever shares or agent use change. Absent means nobody is granted and the agent may not use the item. The signature is HMAC-SHA256 under `HKDF-SHA256(accountKey, salt: empty, info: "teanode passwords access record v1", 32 bytes)` over the UTF-8 bytes of that label, 0x00, the item id, 0x00, the item kind, 0x00, the version in decimal, 0x00, `1` or `0` for agent use, 0x00, then each grantee as `u:<user id>` or `c:<circle id>`, sorted bytewise, each followed by 0x00. Each change by an owner's device sets `recordVersion` one above the highest it has seen. An owner's device that opens its own item checks the signature; a missing or wrong signature, or no record, means the record reaches nobody and the agent may not use the item, nothing is sealed for anyone, and the item says "Sharing could not be checked" with an action to set sharing again, which writes a fresh record on the person's tap. Each device remembers, for each item, the highest version it has seen with a valid signature (the dashboard in `localStorage` for each person, the iPhone in the Passwords keychain group, the command line in its keys file); a lower version is an old record shown again, so the device does nothing automatic with the item (no re-key, no waiting seals, no agent copy) and says "This item's sharing was changed back by the server". Recipients ignore the record, since they cannot check it. The server's agent opener cannot check it either (it has no account key); it requires `isUsableByAgent` in the record and the server flag, and the protection against a forged consent is that the owner's devices never make an agent copy from a record they cannot verify. A device seals an item key for a recipient only if the record reaches them (a person by user id, a circle member when the server lists them in that circle). The helpers are `macOfAccess`, `withSignedAccess` and `verifyAccess` in each language, and the vectors carry one signed record.
- **Automatic re-keys never widen.** A re-key the person did not start (the server's `needsNewKey` mark seen on open, on sync or before a save) seals only for people in the verified record who already had a key for the item when it last saw it (each device keeps a list of user ids it sealed for or saw holding keys), and for the agent only if the verified record says so and the item had an agent copy when last seen; anyone else the record reaches is sealed for when the device completes waiting shares or the person asks for a re-key. An item is re-keyed automatically at most once in 10 minutes, and at most 20 automatic re-keys are made in a session (the command line: in one command); past that the item is shown as needing attention. A re-key the person asks for (`teanode passwords rekey`) seals for everyone the record reaches. No device cuts the record on the server's word.
- **Share keys name their item key.** Every key sent with `AddPasswordShareKeys` or `SetPasswordItemShares` also carries `itemKey`, the account-sealed item key text the device opened to seal it, and the server refuses one that differs from the item's current key ("changed on another device"). A key row a tap stored is never overwritten except by a re-key; a row stored by a token may be replaced by a later tap.
- **Passphrase rules.** The iteration count must be between 600000 and 10000000 on every client and on the server, and a passphrase has at least 12 characters.
- **Server agent key.** One P-256 key pair per server; the private scalar sealed by `secretbox` with the label `teanode passwords: agent key-v1`.
- **One-time codes.** RFC 6238 from an `otpauth://totp/...` URI: `secret` (base32, case-insensitive, padding optional), `algorithm` SHA1 (default), SHA256 or SHA512, `digits` 6 (default) or 8, `period` 30 (default).
- **Passkeys** (ES256 only, COSE algorithm -7). The private key is PKCS#8 DER in base64 inside the login's fields. Registration: a 16 byte random credential id; authenticator data = SHA-256(relying party id) (32) || flags || sign count 0 (4 bytes big-endian) || AAGUID (16) || credential id length (2 bytes big-endian) || credential id || the COSE public key (CBOR map `{1: 2, 3: -7, -1: 1, -2: X, -3: Y}` with canonical key order 1, 3, -1, -2, -3); flags `0x5D` (UP, UV, BE, BS, AT) when the person was verified, `0x59` when not; attestation object = CBOR map `{"fmt": "none", "attStmt": {}, "authData": <bytes>}` in that key order. Sign-in: authenticator data = SHA-256(relying party id) || flags (`0x1D` verified, `0x19` not) || sign count 0; the signature is ECDSA P-256 SHA-256 over authenticator data || client data hash, DER encoded. TeaNode's AAGUID is the fixed 16 bytes `5445414e-4f44-4550-4153-53574f524453` (the ASCII of "TEANODEPASSWORDS").


### Item fields (inside the encryption)

- Login: `name`, `userName`, `password`, `sites` (list of URLs), `oneTimeCodeUri` (`otpauth://`), `notes`, `passkeys` (each `credentialId`, `relyingPartyId`, `userHandle`, `userName`, `userDisplayName`, `privateKey` (PKCS#8, ES256), `createdAt`), `folder`.
- Card: `name`, `cardholderName`, `number`, `expiryMonth`, `expiryYear`, `securityCode`, `brand`, `notes`, `folder`.
- Note: `name`, `text`, `folder`.
- Every kind may also carry `access`, the record in Known keys above. Every client keeps it through edits (an edit must never drop or widen it) and the readers accept exactly that shape and refuse any other as unreadable. Exports leave it out.

### Storage (migration `0251_passwords`, with `.reverse.sql` and a reverse test like its neighbours)

- `password_setup`: `user_id` (primary key), `account_key_by_passphrase`, `passphrase_salt`, `passphrase_iteration_count`, `passphrase_proof_hash`, `account_key_by_recovery_key`, `recovery_key_proof_hash`, `public_key`, `private_key_by_account_key`, `lock_after_minutes`, `created_at`, `updated_at`.
- `password_item`: `id` (UUID), `owner_user_id`, `item_kind` (`login`, `card`, `note`), `encrypted_fields`, `item_key_by_account_key`, `revision` (bigint, raised on each save), `is_usable_by_agent`, `item_key_by_agent_key` (null unless usable by the agent), `last_used_by_agent_at`, `needs_new_key` (set in the same transaction as anything that narrows access: a share removed, a member leaving or removed from a circle, a circle deleted, a delete of an item that had keys or an agent copy, the agent switched off; cleared only by `RekeyPasswordItem`; a restore keeps it), `deleted_at` (kept 30 days, then removed), `created_at`, `updated_at`.
- `password_share`: `id`, `item_id`, `owner_user_id`, `grantee_user_id` or `grantee_circle_id` (exactly one), `created_at`.
- `password_share_key`: `item_id`, `recipient_user_id`, `item_key_by_recipient_key`, `recipient_public_key` (the key it was wrapped for), `created_at`; primary key (`item_id`, `recipient_user_id`). A circle share has a row per member with Passwords set up; a member without one, or who joined later, is listed as waiting until an owner's device adds their row.
- `password_item_version`: `item_id`, `revision` (the one the item had before the save), `encrypted_fields`, `item_key_by_account_key`, `replaced_at`; primary key (`item_id`, `revision`). A save that replaces an item first copies what it replaces here; a version is kept only if the item has no kept version younger than an hour, or if it holds content the person saved by tap and the save replacing it was not a tap (up to 20 of those for an item), for 30 days and at most 60 of the others an item, dropping the one just before the newest past that (the hourly sweep that removes deleted items removes older versions). The person lists them and puts one back with `ListPasswordItemVersions` and `RestorePasswordItemVersion` (a tap only). The table keeps no time for when the content was saved, so `savedAt` is `replaced_at`, when a later save replaced it. `password_item` carries `item_bytes` (generated: its fields and keys) and `versions_bytes` (kept by a trigger on this table), so that the sum of what a person holds does not read their versions.
- `password_agent_key`: one row, `public_key`, `private_key_sealed`.
- Permission `passwords:use`.

### GraphQL (`internal/api/v1api/apigraph/passwords.go`)

Every operation needs `passwords:use`; a person without it is told "not found". Every sealed value is a `String` holding the JSON of the format above, and the server checks its shape on every input (version 1, a 12 byte nonce, a ciphertext of at least 16 bytes, canonical base64 with no other spelling and no extra field; a key sealed for a key pair also has an `ephemeralPublicKey` of 65 bytes starting with `04`; public keys, salts and hashes are canonical base64 too), and every identifier is a `String` (the schema has no ID type). A revision is an `Int64` (the scalar SkillSharing uses, a JSON number; TypeScript numbers are exact to 2^53, Swift's `Int` and the Go client's `int64` are 64-bit), and a variable that is a fraction or past what a float holds exactly is refused, not cut. An item's `id` is a lower case UUID made by the device, because the encryption names it (the server refuses upper case, and the database checks it too).

Queries:

- `ReadPasswordsSetup`: `isSetUp`, `passphraseSalt`, `passphraseIterationCount`, `publicKey` (null until set up), `lockAfterMinutes`, `itemCount`.
- `ListPasswordItems(sinceRevision: Int64)`: `items` (the person's own, deleted ones with `deletedAt`, and those shared with them for which a key sealed for their current public key is stored, whose `revision` is above `sinceRevision`), `itemIds` (every item they can open now, so a device drops what is gone; an id there that a device does not hold means it asks again from the start), `revision` (the highest visible, 0 with none). One listing runs for a person at a time, and the server holds that place until the answer has been written to the reader (a minute to write it), so slow readers cannot multiply the memory; a second is turned away to try again. The listing reads under a shared advisory lock on the revision lock below, so a change that has not committed is waited for and none can commit between its statements: the revision it answers is never above one that is not visible, and a device that continues from it skips nothing. An item's `itemKey` is the owner's key sealed by the account key, or for a recipient their own key sealed for their public key, which they open with the item's `ownerPublicKey` (the owner's current public key from `password_setup`, on every item view, `String!`; a device compares it with the key it knows for that owner before using it) and the item's `ownerUserId`; `shares` is the owner's list with each share's `recipients` (name, `publicKey`, `hasKey`) and is empty for anybody else, and `needsNewKey: Boolean!` says the owner's item needs `RekeyPasswordItem`.
- `ListPasswordRecipients(granteeUserId, granteeCircleId)`: the person (in a circle with the caller) or the members of a circle the caller is in, without the caller, who may use Passwords, with the public key each set up (null if none). `hasKey` is false here, since no item is asked about. A person or circle the caller has no reach to is "not found", as in Health.
- `ListWaitingPasswordShares`: for the caller's own items, each recipient a share reaches who has set up Passwords and has no key sealed for their current public key and does not have too much shared with them (`itemId`, `recipient`).
- `ListPasswordItemVersions(itemId)` (tap only): the owner's kept versions of an item, newest first: `versionId` (the revision the item had then, as text), `savedAt` (when a later save replaced it), `isSavedByPerson`, `encryptedFields`, `itemKey` (the account-sealed item key of that version), `itemKind`. An item that is not the caller's is "not found".
- `ReadPasswordsAgentKey`: the base64 public key (65 bytes) of the server's agent key, made on first use. The private scalar is sealed under the secretbox label `teanode passwords: agent key-v1`.

Mutations (a "tap" is `IsPersonsTap`: the dashboard or the iPhone app, not a command line token, with the `api.TapRequiredPhrase` refusal):

- `SetUpPasswords(input: PasswordsSetupInput)` (tap; refused with "Passwords is already set up."): `accountKeyByPassphrase`, `passphraseSalt`, `passphraseIterationCount`, `passphraseProofHash`, `accountKeyByRecoveryKey`, `recoveryKeyProofHash`, `publicKey` (checked to be a P-256 point), `privateKeyByAccountKey`. `passphraseIterationCount` must be from 600000 to 10000000 here and in `ChangePasswordsPassphrase`.
- `UnlockPasswords(proof, isRecoveryKey)`: `accountKeyWrapped` (by the passphrase, or by the recovery key with `isRecoveryKey`), `privateKeyByAccountKey`, `publicKey`. Wrong proofs say "That passphrase is not right." or "That recovery key is not right.", are limited to 10 in a row for each person on an instance, counted apart for their taps and for other credentials (30 an hour given back, in memory like the sign-in limits; a try is taken before the proof is checked and given back when the proof is right, so proofs sent at the same moment cannot all be judged before the first wrong one is counted), and are written to the audit log without the proof.
- `ChangePasswordsPassphrase(input: PasswordsPassphraseChangeInput)` (tap; `proof` of the old passphrase, or of the recovery key with `isRecoveryKey`) and `ReplacePasswordsRecoveryKey(input: PasswordsRecoveryKeyReplacementInput)` (tap; `proof` of the passphrase). Both answer the setup.
- `UpdatePasswordsSettings(lockAfterMinutes)` (1 to 10080; a tap when it makes the time longer than it is), `ErasePasswords` (tap; answers true).
- `SavePasswordItem(input: PasswordItemInput)`: `id`, `itemKind`, `encryptedFields`, `itemKey`, `baseRevision` (null for a new item). Owner only. A `baseRevision` that is not the current one is refused with "This item changed on another device. Open it again."; the kind cannot change; a deleted item cannot be saved.
- `RestorePasswordItemVersion(itemId, versionId, baseRevision)` (tap only; `Int64` revision): makes that version's fields and item key the item's own, keeps what it replaces as a version (whatever the one-hour rule says), deletes every key stored for a recipient and the agent's copy (the agent's use ends), marks the item `needsNewKey`, and gives it the next revision; the device then re-keys it at once. A `baseRevision` that is not the current one is refused as changed on another device; a deleted item, a version that is not kept and somebody else's item are "not found".
- `DeletePasswordItem(id)`, `RestorePasswordItem(id)`, `PurgePasswordItem(id)`: a delete keeps the item 30 days, ends the keys sealed for its recipients and the agent's use, and marks it `needsNewKey` when anybody held a copy; a restore leaves the recipients waiting and keeps the mark; a purge (a tap only) removes a deleted item and its old versions at once, and is the only way to free the allowance for deleted data before the 30 days are up.
- `SetPasswordItemShares(input: PasswordItemSharesInput)`: `itemId`, `grantees` (`granteeUserId` or `granteeCircleId`), `keys` (`recipientUserId`, `itemKeyByRecipientKey`, `recipientPublicKey`, `itemKey`). It replaces the item's shares; a tap is needed when it adds a grantee (keeping or narrowing needs none). A key's recipient must be reached by a grantee, else "not found"; its `recipientPublicKey` must equal their current one, else "That person's key changed since it was read." Keys of people no longer reached are deleted. Nothing is stored when it is refused.
- `AddPasswordShareKeys(keys: [PasswordItemShareKeyInput!]!)`: the same keys with an `itemId` and the `itemKey` each was sealed from (required), for recipients already reached (the waiting ones); no tap, since it widens nothing; a key row already stored by a tap is left as it is, and one a token stored is replaced only by a tap; counts a write for each item named; answers how many were stored.
- `RekeyPasswordItem(input: PasswordItemRekeyInput)` (operation 18; no tap): `id`, `baseRevision`, `encryptedFields` and `itemKey` sealed under a new item key, `shareKeys` (the keys `AddPasswordShareKeys` takes, with `itemKey` optional since they are sealed from the new key in the same call, each for a recipient a share reaches now and sealed for their current public key, else refused) and `itemKeyByAgentKey` (replaces the agent copy when the agent uses the item, null ends the agent's use, and it must be null when the agent does not use the item). It deletes every key stored for a recipient and stores the given ones, so a recipient given none waits; one revision, the replaced version kept as a save keeps it. It clears `needsNewKey` and works on a deleted item too, so a restore can be followed by a re-key. Refused with "Passwords is full: delete items or make notes shorter." when the new item would take the person past 64 MiB of items that are not deleted; saves and restores are too. Deleted items and kept versions have their own 128 MiB allowance, and when it is full a change that is not a tap and would add to it is refused ("Passwords is keeping too many deleted items and old versions") while a tap always goes ahead. Every write mutation above is limited for each person (5000 in a row, 5000 an hour given back, a call that names several items counts each) in a bucket for the person's taps and another for every other credential, and answers "too many attempts" past it.
- `SetPasswordItemUsableByAgent(input: PasswordItemAgentUseInput)`: `itemId`, `isUsableByAgent`, `itemKeyByAgentKey` (needed to turn it on). Turning it on needs a tap; turning it off does not, and marks the item `needsNewKey`. A card is refused with "A card cannot be used by the agent."

Revisions come from one sequence, drawn under an advisory lock held until commit so that numbers are committed in the order they are drawn and a device that has seen N has seen everything below it. A save, a delete, a restore, a change of shares or keys, a change of the agent's use, and a person leaving the circle that made a share possible each give the affected items the next number. The agent using an item does not: it sets only `last_used_by_agent_at`, so a device that has the item open can still save it, and a device sees the new time on its next full read. A mutation that is refused after writing something would be committed with the rest of the request, so the ones that can refuse late (shares and keys) run under a savepoint. Items deleted more than 30 days ago are removed by the hourly sweep that removes expired sessions and tokens (`authenticator.Scavenge`). The audit log has `passwords` (set up, passphrase and recovery key changes, unlocks, unlock failures, tries turned away for being too many, erase) and `password_item` (saved, deleted, restored, version restored, shares changed, keys added, agent use changed, used by the agent) events, with ids, kinds, revisions and grantees, never a sealed value, key or hash.

### The agent (`internal/agent/tools/passwords/`)

- `passwords` tool, actions: `list` (the items the person let the agent use: name, kind, sites, user name; never a password, code or card number), `read_note` (a note the agent may use), `generate` (a new password, never stored by the agent).
- The browser tool gains `fill_login` (item id, the user name and password fields by snapshot reference), `fill_one_time_code` (item id, field reference) and passkey sign-in: in the headless browser through CDP's WebAuthn domain (a virtual authenticator holding only that passkey, removed after the sign-in); in the attached tab by asking the extension through the attached tab's existing `act`/`result` pair (#612's protocol), with the actions `fill_login`, `fill_one_time_code` and `passkey_sign_in` whose arguments the server builds; the extension's `PROTOCOL` goes to 5 and the server checks it as it checks casting for 4. While the person has taken over the tab, these are refused like every other acting action (only reading actions run), so the agent never fills while the person holds the tab; a fill the person starts from the extension is theirs. The content scripts never detach the debugger the agent and the live view share.
- Each refuses an item not usable by the agent ("Turn on Let the agent use this on the item first"), a page whose origin (host and port) does not match the item's sites, a card, a run the person did not start, and a person who no longer holds `passwords:use` (asked again whenever an item is opened). A field takes only its own kind: a password goes into a password input (or one whose autocomplete says `current-password` or `new-password`), a user name into a text, email or telephone input (or autocomplete `username` or `email`), a code into a text, number or telephone input (or autocomplete `one-time-code`); a textarea, a select and an editable region are never filled. `docs/subsystems/passwords.md` says how a filled page is locked and scrubbed.
- A site the agent ran script on is never filled again in that browser. The headless browser clears it with the action `reset`, which opens a fresh browser context; in the person's tab the extension keeps the sites (`scriptedOrigins`) and the options page's "Allow the agent to fill on these sites again" clears them.
- The agent's reach through the attached tab is an exact list of DevTools methods with no file or drag methods, no TeaNode or extension pages, no input into the person's TeaNode panel (`docs/subsystems/devices.md`), and the extension offers or fills nothing in a tab the agent drove in the last minute unless the person holds the tab.
- Private turns: a turn that listed items, read a note or made up a password, or whose subagent did, is hidden from every run the person did not start, from compaction, from conversation search (except a tap's) and from push text. `list`, `read_note` and `generate` are refused in a subagent. A schedule the agent wrote cannot use Passwords until the person opens it on the dashboard or in the app and saves it with its prompt (a tap's save that includes the prompt takes it over).

### The command line (`internal/client/passwords.go`, `internal/cmd/passwords.go`)

`teanode passwords setup | unlock | lock | list | show | copy | add | edit | delete | restore | share | unshare | trust | code | rekey | agent | generate | import pass | import csv | export`. It asks for the passphrase (never in an argument or environment variable; `--passphrase-stdin` for scripts), at least 12 characters when it makes one. `setup` asks the server whether this connection may set up (it sends an empty setup, which the server refuses for want of a tap before it looks at the input) before it asks for a passphrase. `unlock` keeps the opened keys in a file readable by its owner only, only in `$XDG_RUNTIME_DIR/teanode` (a folder of the login that is not on disk); where there is none it refuses, and each command asks for the passphrase instead. The file lasts the lock time but never more than 8 hours; a file that others could read or change, that is a link, or that belongs to somebody else is refused, and an expired one, or one an earlier build left in the configuration directory, is removed by the next command. Each profile keeps the known keys, the highest access record version seen for each item and who held a key for it in `passwords-keys-<profile>.json` in the configuration directory (also mode 0600): `share`, `share --waiting` and the re-key ask nothing about keys: they seal for the known or first-seen key and only for people the signed record reaches, and print one line for each first-seen or changed key ("first key for ben recorded", "ben's key changed: compare codes with teanode passwords code"). `teanode passwords trust <user name> <safety code>` (32 digits, spaces optional, or `--code-stdin`) is the optional way to mark codes compared and gates nothing; it refuses a server that answers with another person than the one named, records a match as compared, and never prints the code it expected on a mismatch. `teanode passwords code` prints the person's own safety code, worked out from the key pair unlocking opened (`--json` too). `unshare` and `agent off` re-key the item. When the server marks an item `needsNewKey`, `edit`, `share`, `unshare` and `agent` re-key it first (automatically only for people and the agent this computer last saw holding a key, at most once in 10 minutes for an item and 20 in one command), `list` and `show` say "needs a new key: run teanode passwords rekey <item>", and `teanode passwords rekey <item>` seals for everyone the signed record reaches, and before it seals it says who that is (the people, whether the agent gets a copy, who waits) and asks for `yes` at a terminal, or requires `--yes` without one; `list` and `show` name the same people under an item that needs a new key. An item whose record is not signed or is an old one shown again is left alone: `unshare` and then `share` write a fresh record. `delete --forever` removes an item that is already deleted, which needs a tap, so it says where to do it. `copy` clears the clipboard after the time given, on Ctrl-C and when asked to end, and only if the clipboard still holds the secret (read back where the clipboard program can). Changing the passphrase or the recovery key makes the old one stop opening Passwords on this server; it does not make a new account key, so a copy of the database from before still opens with the old one. `import pass` runs `gpg` on the person's own machine, reads the first line as the password, `login:`, `user:`, `username:`, `email:`, `url:` lines and an `otpauth://` line, and keeps the rest as notes; the path becomes the folder and name; the path is given to gpg after `--`. `import csv` reads Chrome's, Apple Passwords' and Bitwarden's CSV exports.

### The dashboard (`web/src/pages/passwords/`)

An unlock screen, the list (search, folders, kinds), an item with its fields hidden until shown, copy buttons, the one-time code ticking, the editor with a generator, Share (circles and people, Compare codes, waiting recipients), Let the agent use this, Recently deleted, and a Settings tab (your safety code, passphrase, recovery key, lock time, import, erase). Locked again after the lock time or on reload. It seals only by the signed access record, for the known or first-seen key of each person, with no prompt about keys; it shows a notice with Compare codes when a person's key changed, re-keys an owned item the server marks `needsNewKey` when it opens Passwords and before saving it (never widening, with the cooldown and cap above), completes waiting shares when the recipient has a key, shows "Sharing could not be checked" and "This item's sharing was changed back by the server" with "Set sharing again", keeps what the person typed when a save conflicts, and offers Delete forever in Recently deleted.

### The Chrome extension (`web/extension/src/passwords/`)

Version 5.0.0 of the extension, protocol 5 (the server checks it as it checks casting for 4). The code is TypeScript compiled by `webpack.extension.config.js` with the dashboard's own rule, and imports the dashboard's `src/passwords` and `passwordsProtocol.ts` (the steps on keys), so there is one implementation of the format on the web.

- **Where the keys live.** The opened account key and key pair are in `chrome.storage.session` only (memory, closed to content scripts, gone when the browser closes) as `passwordsKeys`, with the lock time from `ReadPasswordsSetup.lockAfterMinutes` and the time of last use. A one minute alarm drops them after the lock time of no use; they are also dropped on browser start, on signing out or changing the server on the options page, and by the window's Lock. The decrypted list is never stored: each thing the extension does (a suggestion, a fill, a search, a save) fetches the sealed items, opens them in the service worker for that one thing, overwrites the item keys and lets them go. `chrome.storage.local` holds only public data: the known owner keys of shared items (`passwordsPins:<user id>`: an owner's first key is kept once an item from them opened with it, and a changed one is accepted with a notice in the window that can show both safety codes; it gates nothing, and that owner's items keep opening) and whether Passwords is set up. The extension never seals keys for anybody and never re-keys: it refuses to save over an item the server marks `needsNewKey` and says to open Passwords on the dashboard or the iPhone first, and it keeps the access record through edits.
- **The window** (`passwords.html`, a popup window opened by the suggestion, the shortcut Ctrl+Shift+L / Command+Shift+L, the context menu entry *Fill from TeaNode Passwords* on an editable field, or the options page). Unlock with the passphrase or the recovery key through `UnlockPasswords` with the extension's token (not a tap, and needs none); the logins for the page it was opened for first, then a search across all; Fill (sent to the content script of the frame it was opened for, which fills the form around the field last used); copy password, user name or one-time code, cleared from the clipboard after 30 seconds if unchanged (an offscreen document does the copy and reads it back, since a worker has no clipboard); the generator; Lock; a link to the dashboard's Passwords page. English only, like the options page and panel.
- **The suggestion** is `suggestion.html`, an extension page in an iframe inside a closed shadow root, inside one host element placed in the top layer, drawn under a focused, visible user name, password or one-time code field (detected by `autocomplete` hints, `type=password` and, beside a password field, the field's name). It is shown on focus only, never on page load. The service worker answers the content script with the logins whose saved site matches the frame's own address (exact host, `www.` ignored, never `http` unless the saved site is `http`); the page never sees the list. A choice is acted on only when (1) the click is trusted and the browser's visibility tracking (`IntersectionObserver` v2, `isVisible`) says the frame has been fully visible for 400 ms, and (2) the content script's own check (`frameVisibility.ts`) finds the host element and everything around it displayed, opaque, unfiltered, unclipped and unblended, nothing else on top at its middle and corners (`elementsFromPoint`), and no other popover, modal dialog or full screen element open. The message must come from the frame's own window with the extension's origin. Only then does the content script ask the service worker for the secret, which checks the frame's address against the item's sites again before replying, and only visible fields are typed into. A frame whose origin differs from the page around it asks the person first, naming both hosts.
- **Saving.** A submitted form (the `submit` event, or a click on a button or Enter in a password field for pages with no form) with a password sends the user name and password to the service worker, which keeps them in memory only (a `Map`) for two minutes. The next page that finishes loading in that tab without a visible password field (a failed sign-in shows one again), or a page that stays and loses its password field, shows `bar.html` at the top: *Save this login to TeaNode Passwords?* or *Update the password for ada@example.test?* with Save and Not now. Saving needs the unlocked session; locked, the bar's button opens the window to unlock and the window offers the waiting login with a Save button. Never offered in a private window; a user name first sign-in carries the user name over to the password step on the same host.
- **Passkeys.** A script in the page's own world at `document_start` (`mainWorld.js`) replaces `navigator.credentials.create` and `.get` for `publicKey` requests only and passes everything else to the saved originals; `get` with `mediation: "conditional"` also goes to the browser in this version. It copies the options as plain data (binary as base64url) and relays them to the isolated content script, which adds nothing from the page: the service worker takes the origin and address from the browser's description of the sending frame, and whether some page above has another origin from the content script. The service worker checks that the relying party id is the page's host or a domain above it that is not a public suffix (a built-in list of common ones, not the full list) and not an address, makes the ceremony a window of the extension's own (`prompt.html`) asks the person about, and builds `clientDataJSON` itself. A create makes an ES256 passkey (attestation `none`, flags 0x5D, the plan's AAGUID) and saves it into the login for that site and user name, or a new login, before the site gets the credential; a sign-in signs with the chosen passkey. Locked, the window asks to unlock. *Use the browser instead*, no ES256, a security key request, a page without a secure context, a frame of another origin than its page, and a private window all go to the browser. A relying party that is not the page is refused as a browser refuses it (`SecurityError`). The object given back looks like a `PublicKeyCredential` (own `rawId`, `response`, `getClientExtensionResults`, `toJSON`; `authenticatorAttachment: "platform"`).
- **Review fixes (security).** A suggestion is shown and a sign-in remembered only when `navigator.userActivation.isActive` (a script cannot make a gesture); a press on a focused field asks for the suggestion. What a field was told is kept ten seconds in the worker (names only, by origin and field kind) so a page that moves the focus about cannot make it open the list over and over. The frames talk to the content script over a `MessageChannel` handed over once after load, addressed to `new URL(frame.src).origin`; a frame that does not answer in three seconds is closed. The down arrow in the field moves into the frame, Enter fills, Escape and Tab out return to the field. A field is visible only if the product of opacities is at least 0.5, no clip path, clip or overflow cuts it off, and `elementFromPoint` at its middle is the field; a form whose `action` or any `formaction` (read as attributes) goes to another host than the page's is filled only after the person says yes (the agent's fill refuses). Sites are read with `new URL` (a bare host gets `https://`), a backslash or control character is refused, and a login matches by origin including the port, the cases shared with Go in `internal/passwords/testdata/sitematch.json`; the window's fill carries the approved origin to the content script. A passkey sets the user verified flag only within 60 seconds of typing the passphrase (`verifiedAtMilliseconds` beside the keys in `chrome.storage.session`); `userVerification: "required"` waits for the passphrase in the prompt. The prompt names the page's origin, opens unfocused when its tab is not the active one, ends on the page's cancel message, on `tabs.onUpdated` to another address and on tab close, and no passkey is saved after the page is gone. Locked, a sign-in for a site with no known passkey goes to the browser without a window (the sites with a passkey are kept as salted hashes in `chrome.storage.local`), "Use the browser instead" is remembered per origin for the session, and `create` with conditional or silent mediation and `get` with silent mediation go to the browser. The service worker closes `chrome.storage.local` and `chrome.storage.sync` to content scripts at start; the panel script gets the token only after the button press on its tab. The relying party may not be an address (except `127.0.0.1`), and the shared hosting suffix list is longer. `lockAfterMinutes` is capped at 1440. A shared login whose owner key changed is counted and the window says so. The offscreen document answers only the service worker, and its creation and closing are serialized. Server text is mapped to friendly words except the sentences written for people.
- **The agent.** `fill_login` and `fill_one_time_code` in the attached tab: the extension checks the call is for the tab the actions go to (`expectedTab`), that the tab's host and port equal the ones named, that the page is https (or a local test page), then types by snapshot reference into visible, enabled fields of the right kind after checking the page's own address again. Before it types it turns the tab's `Network` capture off and forgets the events it kept. ## Idempotence and Recovery

Saving sends the revision it was based on, so a retry or two devices racing cannot overwrite silently. Import skips an item whose kind, name, folder, first site, user name and its password (or note text) are all the same as one that exists, compared as the text itself in the command's memory for that one import (no digest of the secret is made or kept), and names what it skipped; an item that differs in any of them is kept as a second item. A save that replaces an item keeps the version it replaced for 30 days (`password_item_version`: at most one an hour and 60 in all, and every version the person saved by tap, up to 20, so no number of saves from a token pushes them out), so a bad overwrite can be put back from the database; there is no API to restore a version, since the keys sealed for recipients and the agent belong to the item key of one version. Erasing Passwords is the only recovery when both passphrase and recovery key are lost; it says so before it asks. The tap guards erasing, not saving: a token with `passwords:use` that is not the person's tap (a command line's, say) can still save any item over with something of the right shape, which is as bad as an erase for that item, and the 30 days of versions are what bring it back.
