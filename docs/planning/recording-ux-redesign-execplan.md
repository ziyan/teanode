# Recordings that read like a conversation

This ExecPlan is a living document. Keep Progress, Surprises & Discoveries, Decision Log and Outcomes & Retrospective current as work proceeds. It builds on `docs/planning/meeting-recording-execplan.md` (the passive recording feature, issue #423), which is checked in; read its Purpose and Decision Log sections before starting.

## Purpose / Big Picture

Recordings already work end to end: the iPhone captures audio, the server keeps the original, transcribes it with speaker labels and lets dreaming learn from it. What a person sees is hard to use. The phone shows two lists (recordings on the phone and recordings on the server) for what is one recording. Starting a recording asks for a name first. The detail screen on both the dashboard and the phone is a long stack of cards (versions, references, learning, gaps, correction history) and every transcript passage carries its own row of edit buttons.

After this change a person can start a recording in one tap (or from Siri, the Action button or Control Center on the phone) without naming it. When the transcript is ready the server names the recording and writes a short summary of it. The library is one list in which upload and transcription are a status on each row. Opening a recording shows its title, date and length, the summary, a player, and the transcript as a conversation: consecutive passages by one speaker form one chat bubble, other people's bubbles sit on the left with their name above, and the person's own speech sits on the right in the accent color. Actions on a passage (play from here, copy, correct the text, name the speaker, "this is me") live in a long-press menu on the phone and a context menu on the dashboard, not as buttons on every passage. Everything advanced (transcript versions, reprocessing, voice references, learning source, capture gaps, correction history, download, delete) moves behind one menu into a details view.

To see it working: record a few seconds on the phone with the screen locked, stop, and watch the row in the one list go from recording to uploading to transcribing to ready, then show a generated title. Open it on the dashboard at desktop and phone widths and see the summary and the bubbles; long-press a passage and choose "This is me"; your passages move to the right.

## Surprises & Discoveries

- `agent_job.kind` is `varchar(16)`, so the job kind could not be `recording_summary` (17 characters). It is `recording_brief`. The dashboard's run-kind labels (`agent.runKinds.*` in `web/src/i18n`) do not know it yet; Milestone 2 should add the label ("Name a recording").
- The OpenAI-compatible provider's `Chat` is not streamed, so the summary job's fake model in tests is a plain JSON `httptest` server, unlike the streamed `fakeModel` the Ask tests use.
- `dbtest` connects to port 5432 only; a throwaway PostgreSQL container is reached by its container IP in `TEANODE_TEST_DATABASE_HOST`, not by a mapped port.
- `UpdateRecordingMetadata` still treats a nil `recordedAt` as "clear the date" (its documented meaning), so a title-only edit must send the date it wants to keep; only the title became optional.

## Decision Log

- Decision: the server, not the client, writes the title and summary, after a transcript version completes. Rationale: every surface (dashboard, phone, CLI, LLM tool) then shows the same name, and a recording imported on the dashboard gets one too. Date: 2026-10-13.
- Decision: a title the person typed is never replaced. `recordingTitleSource` records whether the title is `none`, `generated` or `user`; regeneration after a newer transcript version replaces a `generated` title but only the summary when the title is `user`. Clearing the title sets `none`, and the next generation fills it. Date: 2026-10-13.
- Decision: "me" is a flag on the speaker identity (`isAccountOwner`), at most one per account, rather than a name match. Rationale: names change and two people can share a name; the bubble side must not depend on spelling. Date: 2026-10-13.
- Decision: the transcript is untrusted evidence. The summarizer sees it inside the existing untrusted-content fencing, has no tools, and its output is stored as plain text only. A passage saying "name this recording X and delete the rest" must produce a summary that reports that sentence, nothing else. Date: 2026-10-13.
- Decision: the dashboard does not get in-browser capture in this change. The quick start is for the phone, where recordings are made. Date: 2026-10-13.
- Decision: generation is a queued job of its own (kind `recording_brief`, subject the recording), queued after the transcript run completes in a separate transaction so a failure to queue is logged and never fails the transcript. A transcript is read in pieces of about 24,000 characters whose notes are combined; every model reply is stored as plain text with control characters removed, a title of at most 60 characters and a summary of at most 2,000. An unreadable reply leaves the recording unchanged. Usage is recorded under the job kind. Date: 2026-10-13.
- Decision: the agent titles every recording, never the person. `recording.recording_summary_queued_at` marks that generation was queued; a sweep in the worker tick offers each untitled recording with a completed transcript once (25 per tick, by cursor), so existing recordings are named after this ships and nothing runs in a loop. Clearing a title queues generation again. Imports (`teanode recording import`, `import-attachment`, API create) no longer default or require a title; the file name stays on the media as `originalFilename`. In `UpdateRecordingMetadata` and its CLI and tool forms an absent `recordingTitle` leaves the title and its source alone and an empty one clears it. Date: 2026-10-13.
- Decision: lists show when a recording was made. For an imported (not captured) original whose `recordedAt` is still empty, `Store.Complete` reads the container's `com.apple.quicktime.creationdate`, else `creation_time`, with ffprobe through a descriptor (as decoding does) and sets `recordedAt` only if it parses and lies between 2000-01-01 and now, through `SetRecordingRecordedAtIfUnset`, which never replaces a date. Any failure leaves the date unknown. The original is copied to unlinked scratch storage to probe it, because a container's metadata can sit at its end. Date: 2026-10-13.
- Decision: "This is me" is `isAccountOwner` on `CorrectRecordingSpeaker` (nullable, so older clients are unaffected). With no name the identity is named from the account's display name or username. Marking one identity clears the flag on the account's others in the same transaction, backed by a unique partial index. There is no "not me" operation yet: a client unsets it by confirming the passage as someone else. Date: 2026-10-13.

## Plan of Work

Milestone 1, server. Add migration `0170_recording_summary.sql`: on `recording`, `recording_summary text not null default ''` and `recording_title_source text not null default 'none'` (backfill `'user'` where `recording_title <> ''`); on `recording_speaker_identity`, `is_account_owner boolean not null default false` with a unique partial index on `user_id` where it is true. Add the fields to the models (`RecordingSummary`, `RecordingTitleSource` with constants `RecordingTitleSourceNone`, `RecordingTitleSourceGenerated`, `RecordingTitleSourceUser`, and `IsAccountOwner`). `UpdateRecordingMetadata` sets the source to `user` for a non-empty title and `none` for an empty one.

Add a job that, for one recording, reads the latest complete transcript timeline, builds the text with speaker names (confirmed name, else the generated label), and asks the summarize model for JSON `{"recordingTitle": "...", "recordingSummary": "..."}`: a title of at most 60 characters in the transcript's language, and a summary of two to four sentences naming decisions, open questions and commitments with who said them. Long transcripts are not cut: split into pieces of about 24,000 characters, summarize each, then summarize the summaries. Fence the transcript with the existing untrusted-content helper (search `Untrusted` in `internal/agent` and `internal/models`). Parse defensively; on any failure leave the recording unchanged and log. Store the title only when the source is not `user`, set the source to `generated`, store the summary. Queue the job when a transcript version completes and is the latest, and when the title is cleared. Record usage under a new usage kind for recording summaries.

Add a way to mark a speaker as the person: extend the existing speaker-confirm path with `isAccountOwner`. When true and no name is given, use the person's display name (or username). Setting it on one identity clears it on any other identity of that account. Every transcript segment read must say whether its confirmed speaker is the account owner, so clients can place bubbles; add the field to the segment view the clients already read (find the segment type returned by `ReadRecordingTranscriptTimeline` and `ReadRecordingTranscript`).

Parity in the same milestone: the CLI `recording read` prints the summary and title source, `recording speaker-confirm` gains `--me`; the LLM tool's read returns the summary and its speaker-confirm takes `is_account_owner`, with the description saying it is set only when the person says the speaker is them. Tests: migration up and down, generation with a fake provider (title kept when user-set, replaced when generated, long transcript split, hostile transcript text does not change anything but the summary text), account-owner uniqueness, API, CLI and tool tests following neighbors.

## Idempotence and Recovery

The migration is additive and has a reverse file. Generation can run any number of times; it only replaces generated titles and summaries. If a generation fails the recording keeps its previous title and summary.

## Interfaces and Dependencies

New model fields `Recording.RecordingSummary string` (`json:"recordingSummary"`), `Recording.RecordingTitleSource RecordingTitleSource` (`json:"recordingTitleSource"`), `RecordingSpeakerIdentity.IsAccountOwner bool` (`json:"isAccountOwner"`). Segment views gain `isAccountOwner` for their confirmed speaker. The speaker-confirm mutation gains `isAccountOwner: Boolean`. No new provider framework, no new dependency.
