# Dictation and voice messages: speaking instead of typing, and holding to talk in people chats

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds. It follows ~/.claude/PLAN.md and builds on docs/planning/voice-input-execplan.md (the drawer's call with the agent), whose socket it reuses.


## Purpose / Big Picture

Today a person can call their agent (the drawer's telephone, the iPhone's waveform button), but every other box has to be typed into. After this plan they can:

1. Dictate. A microphone button in the agent conversation composer, the people chat composer and the journal's "Your words" editor puts what they say into the box as they speak. The words stay editable, and nothing is sent until they press send or save.
2. Send voice messages in people chats. The chat composer gets a keyboard or voice mode, like a familiar messaging app. In voice mode the text field is replaced by a wide "Hold to talk" button: hold to record, release to send, slide up to cancel. A button beside it switches back to the keyboard, and the device remembers the mode. The message arrives as a voice bubble with a play button, a waveform and its length. The server transcribes it, and the words appear under the bubble a few seconds later. Anyone in the chat taps to play it. An agent that reads the chat reads the transcript.

To see it working: on a dev server with voice turned on, open a direct chat between two invented people, Mira and Tobias, on two devices. Mira switches to voice mode, holds the button and says "I am leaving the bakery now, see you at six", then releases. Tobias's chat shows a 0:04 bubble at once and his phone says "Voice message (0:04)". The words appear under the bubble moments later, and tapping the bubble plays it. In the drawer, Mira presses the microphone in her main conversation, says "remind me to water the plants", sees the words land in the box unsent, edits them, and sends.

## Surprises & Discoveries

- Voice is off in every people chat today. The drawer hides its telephone with `!isInChat` (web/src/components/agentDrawer.tsx:6492), and the iPhone never loads voice for a chat ("A chat is people: no ideas to start it with, and no call to the agent", ios/TeaNode/Sources/ConversationModel.swift:246-251).
- An audio file sent in a chat today is a download chip on the web (AttachmentChips, agentDrawer.tsx:1858-1885) and a paperclip capsule on the iPhone (AttachmentView, ios/TeaNode/Sources/MediaViews.swift:324-380). Only a file the agent hands over gets a player (agentDrawer.tsx:2011-2014). Nothing draws a playable sound in a chat yet.
- People chats are not searched by global search ("The chats between people are not searched here", internal/api/v1api/apigraph/search.go:236-239). The conversation tool finds a chat by title and people, not by what was said (internal/agent/tools/conversation/conversation.go:28). A transcript therefore adds nothing to search in this plan.
- A chat message's files are copied as JSON onto the message row (`chat_message.attachments`, internal/db/migrations/0194_chat.sql:81). Facts stored on the file row therefore reach every client with the message, with no extra read.


## Decision Log

- Decision: dictation and voice messages are two ideas with two names. Dictation is "Dictate" (a microphone symbol, words into a box, never sent). A voice message is "Voice message" (a waveform symbol; GraphQL `voiceMessage...`, CLI `--voice-message`). Its words are its "transcript", the word recordings already use. The call stays "Call" (the telephone on the web, the waveform in agent conversations on the iPhone). Rationale: the project's one-name-per-idea rule, and Apple's Messages uses the same symbols (microphone for dictation, waveform for an audio message). The iPhone's call button keeps the waveform because calls are never offered in a chat, so the two never meet.
- Decision: the dashboard dictates through the existing socket `/api/v1/agent/voice`, with a new hello field `purpose: "dictation"` and `dictationPlace` (`agent`, `chat`, `journal`). Rationale: the socket already only transcribes and starts no turn (voice-input-execplan.md:57, agent_voice.go:25-32). It streams `transcriptDelta` and `transcriptFinal` per utterance, which is exactly "words into the box". It already signs in, checks budget and records usage. Only the transcription prompt (`voicePrompt`, agent_voice.go:437-443) and the log wording change with the purpose. Dictation is offered when `ReadAgentVoice.isVoiceAvailable` is true. When the operator has voice off, or the person has no active agent, no microphone is shown: the socket would refuse with 403 (agent_voice.go:185-187), and the system's own dictation (the keyboard key, the desktop shortcut) still works in the box.
- Decision (the person, 2026-11-01): the iPhone dictates through the server, like the dashboard: the same socket `/api/v1/agent/voice` with `purpose: "dictation"`, which the iPhone's call already speaks (VoiceCall.swift). The microphone button shows only when `ReadAgentVoice.isVoiceAvailable`; the keyboard's own dictation key still works when it does not.
- Decision: a voice message is a chat message with `is_voice_message` set, an empty body and exactly one file, the recording. Duration and waveform are facts of the file (`agent_attachment.audio_duration_ms`, `audio_waveform`); the transcript is a fact of the message (`chat_message.transcript_text`, `transcript_state`). Metadata in the database, bytes in the blob store through `storage.PutFile` as every attachment (agent_attachment.go:186-191). Rationale: the file facts ride along in the JSON copy on the message; the transcript changes after posting and belongs to the message.
- Decision: the server normalizes every recording to AAC in an MP4 container (m4a), mono. AAC input is remuxed without re-encoding (`-c:a copy`, `-map_metadata -1`, `-movflags +faststart`); anything else (the browser's WebM/Opus) is encoded at 48 kbps. Rationale: the iPhone's AVAudioPlayer does not play WebM, and every browser plays AAC m4a. ffmpeg and ffprobe are in the image (deploy/Dockerfile:46-50) and already run under a protocol and format whitelist in internal/recording/decode.go:39-70 and 100-105, which the new code copies. The browser records `audio/mp4;codecs=mp4a.40.2` where `MediaRecorder.isTypeSupported` says yes, else `audio/webm;codecs=opus`.
- Decision: transcription is server side, after the message is posted, through the provider's file transcription that recordings use. The model is `provider.Name + ":" + agent.voice` transcriptionModel, found as `recordingAccurateModelName` finds it (internal/agent/recording_accurate.go:81-91), selected with `Registry.TranscribingFor(name, false, false)` (internal/llm/transcription.go:88), and called with `MediaContentType: "audio/mp4"`, which the client accepts (internal/llm/openai_transcription.go:158-164). Usage is recorded against the sender's agent with the kind `voice`. Rationale: one place makes one transcript, the same for every reader, and a file sent from the CLI gets one too. The bubble appears at once and the words follow, as people expect from messaging apps.
- Decision: no transcript when the server's voice is off, or the sender's agent is off or over its budget (`transcript_state = 'off'`). The bubble still plays and shows no words. Rationale: transcription is paid for, and a person without an agent has no budget (the upload already skips text extraction for them, agent_attachment.go:150-166).
- Decision: a voice message addresses no agent and mentions nobody, and the transcript cannot be edited (delete and send again). The author may delete it; deleting clears the transcript along with the body and files (internal/db/database_chat.go:1210-1213). A reply to a voice message quotes its transcript, or "Voice message" when there is none.
- Decision: the agent's conversation tool `send` stays text only. Rationale: the agent has no voice of its own in a chat, and a spoken message under the agent's name would be a new idea. Agents read voice messages as `[voice message, 0:12] <transcript>` (or `[voice message, 0:12, no transcript]`) in chat turns, in the tool's `read`, and in chat knowledge.
- Decision: the composer mode (keyboard or voice) is per device, for all chats: `@AppStorage("chatComposerMode")` on the iPhone, `localStorage` key `teanode.chatComposerMode` on the web. Agent conversations always use the keyboard. The browser extension's drawer gets neither dictation nor voice messages, for the reason the earlier plan gave: it is another origin with its own microphone permission (voice-input-execplan.md:70).
- Decision (the person, 2026-11-01): the sender's agent pays for the transcript; with voice off the bubble plays with no words. The sender cannot edit the words (delete and send again).
- Decision (the person, 2026-11-01): a voice message is at most 2 minutes and at least half a second. A shorter hold sends nothing and shows "Hold to record, release to send". From 1:50 a countdown shows, and the recording is sent on its own at 2:00.

## Idempotence and Recovery

The migration only adds columns and an index; the reverse file drops them. Back up the database before deploying, as for any migration. Transcription is claimed and retried, so a crash or a second instance does no harm. A recording that fails to upload stays on the device with a "Try again" toast on the iPhone and in memory on the web until the chat is left.
