# Receipts and annotations on finance transactions

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds. It follows the ExecPlan rules the author keeps in their own notes: self-contained, prose first, every milestone verifiable on its own.


## Purpose / Big Picture

A card charge says where money went but rarely what it bought. A marketplace's or a grocery store's charge line tells the person nothing a month later, while the order email or the itemized receipt says exactly what was in the bag. After this change a person can, on the dashboard, from the command line, or by asking their agent:

1. Write an annotation on any finance transaction ("party supplies"), and see whether they or their agent wrote it.
2. Attach a receipt to a transaction: an email in their TeaNode mailbox, a Gmail message their agent read through the Gmail skill, or a photo or PDF they upload. The receipt is stored line by line (items, discounts, taxes, fees, tips), checked so its lines add up to its printed totals, and matched to the charges it explains.
3. Have receipts read and matched automatically: when TeaNode's mail sorting files a message as a receipt, a background job reads the receipt out of it, checks it, and matches it to the charge, so the transaction dialog shows the items without anybody asking.

To see it working: import or sync a grocery store transaction, deliver an itemized receipt email for the same amount to the person's TeaNode mailbox, wait for the receipt job, open the transaction on the Transactions page, and see the receipt's lines under it with "Balanced" and nothing unexplained. The same receipt shows in `teanode finance receipts` and the agent can answer "what did I buy at the grocery store last week".

Splitting one charge across several spending categories by its receipt is deliberately not part of this plan. The schema carries a per-line spending category for it, unused for now, so that later step needs no migration.

## Surprises & Discoveries

- A mailbox item does not keep its id when it moves: `MoveItems` creates a new `mailbox_item` row in the target folder and expunges the old one. A receipt keyed on a mailbox item id would lose its source the moment a rule or the person files the receipt email away, which is exactly what people do with receipts. The stored message (`mail.id`) keeps its id, and it is also what triage's jobs name as their subject. See the Decision Log.
- `TestMirroredMigrationMarksStoredCopies` reversed migration 0144 alone and applied it again while every later migration stayed applied. Once 0154 added columns to `agent_finance_transaction` after 0144's, re-applying 0144 put its columns after 0154's, and the pooled connection's cached `SELECT *` failed with "cached plan must not change result type". The test now takes 0154 off first and puts it back after, newest first, as a real downgrade does.
- The repository's parity tests name every finance operation by a rule: the CLI subcommand is the operation's name in kebab case and the tool operation in snake case, each with only a leading `Finance` dropped. The plan's names did not all fit it (`AnnotateFinanceTransaction` would be `annotate-finance-transaction`, not `annotate`; `RecordFinanceReceipt` would be `record-finance-receipt`, not `record-receipt`). See the Decision Log.
- The server cannot read a PDF's text: `ExtractAttachmentText` reads text files only, the computer daemon reads PDFs on a person's machine, and no PDF library is vendored. A model is only ever shown text and pictures (`llm.ContentPart`).
- A photo shared in a conversation is named to the model, never given by id, so the agent cannot record it as an `attachment` receipt with the tool; the dashboard's and the CLI's upload to a transaction (Milestone 3's `ReadReceipt`) is the path for photos. The tool still takes `agent_attachment_id`, for parity, described as "only by an id you were given".
- An agent job's subject, and a run conversation's, is `character varying(32)`: one id. The first design put the upload's finance transaction in the subject as `<attachment>/<transaction>`, which the tests caught before it could fail in production. See the Decision Log.
- The end-to-end run found an "order placed" email and its "shipped" email both matched automatically to one charge, and a newsletter quoting a price matched to an unrelated charge of the same amount: the matcher looked only at amounts and never at what other receipts already explained.
- `main` gained its own migration `0153_agent_speech_voice` while this branch was open, taking the number this branch's migration first had. Done: when the branch was rebased onto `main`, the receipts migration was renumbered to the next free number, `0154_finance_receipts`, and the forward, reverse and forward-again proof was run again.
- A finance transaction deleted by a sync (a pending charge replaced by its posted one) takes its receipt matches and annotation with it: `carryPendingDecisions` carries only the spending category and the duplicate decision. The receipt itself stays, unmatched, and the matcher can match it again to the posted charge; the person's annotation on a pending charge is lost. Fixed 2026-10-07, see the Decision Log: the annotation, the receipt matches and the uploads to the pending charge now move to the posted one in the sync's transaction.
- The only path that deletes a finance transaction while a newer copy takes its place is the provider sync (`applyFinanceSync`): Plaid's removals, which name the posted transaction's pending one, and SimpleFIN's `PendingReplacedFrom`. Statement imports hold no pending transactions and never delete one; deleting a finance account deletes its transactions with no copy taking their place. SimpleFIN pairing used to consider only pending charges the person had categorized, so a pending charge with only an annotation or a receipt would not have been paired at all.


## Decision Log

- Decision: the person's or agent's free text on a transaction is called `annotation` (column `annotation`, JSON `annotation`), with `annotatedBy` (`person` or `agent`). Rationale: `note` collides with TeaNode's Notes feature and the `note` tool, and with the memo a bank statement carries; `personNote` is wrong because the agent writes it when asked; `comment` suggests a thread. Date: 2026-10-07.
- Decision: the agent never overwrites an annotation whose `annotatedBy` is `person`, the same rule `CategorizedBy` and `DuplicateDecidedBy` follow. A person always may. Date: 2026-10-07.
- Decision: receipt lines are stored exactly as printed. Tax is never spread into item prices when storing; any sharing out (for the later category split) is computed when totals are read. Rationale: storing as printed keeps the add-up check exact and keeps the transaction, not the receipt, the source of truth for totals. Date: 2026-10-07.
- Decision: receipts and transactions are joined through a match table, not a column on either, because one online order can become several charges (split shipments) and one charge can cover several orders. Date: 2026-10-07.
- Decision: a receipt photo or PDF is an ordinary agent attachment (`agent_attachment` row, bytes in the same `storage.Storage` the mail spool uses, which is local disk mirrored to S3-compatible storage such as MinIO when configured). The orphan scavenger must skip attachments a receipt points at. Date: 2026-10-07.
- Decision: every operation ships on the dashboard, the agent's finance tool and the CLI together, with the same behavior (GraphQL is what all three call). Date: 2026-10-07.
- Decision: a receipt read from TeaNode mail is keyed on the stored message, not the mailbox item: `receipt_source_kind` `mail` (not `mail_item`) and column `mail_id` (not `mail_item_id`), with no foreign key, so a receipt survives the message being filed away or deleted. The API takes a `mailboxItemId` (what mail_search and the dashboard know), checks the person may read it, and stores its mail id; a receipt read back carries `mailboxItemId`, where the message is now, for opening it. Rationale: see Surprises & Discoveries; a mailbox item id changes on every move. Date: 2026-10-07.
- Decision: `subtotal_amount` is nullable. A receipt that prints no subtotal has none; storing a computed one would break "stored exactly as printed". With no subtotal, the check is that every line comes to the total. Date: 2026-10-07.
- Decision: `agent_finance_receipt_match` also carries `agent_id`, as every other finance table does, so reads filter on the owner directly; and `matched_amount` is positive (what the receipt explains of a money-out charge). Date: 2026-10-07.
- Decision: the Go fields for a receipt's lines and matches are `ReceiptLines` and `ReceiptMatches` (JSON `receiptLines`, `receiptMatches`), not bare `Lines` and `Matches`, per the naming rule. A discount names its item by `discountedLineNumber` when written and is kept by `discounted_line_id`; reads carry both. The count on a transaction is `receiptCount`. Date: 2026-10-07.
- Decision: the operations are named so the CLI and tool names follow from the repository's parity rule, which the parity tests enforce: `AnnotateTransaction` (beside `CategorizeTransaction` and `CountTransaction`; CLI `annotate-transaction`, tool `annotate_transaction`), `RecordReceipt` (`record-receipt`, `record_receipt`), `PreviewRecordReceipt` (what `record-receipt --dry-run` and the tool's `preview_record_receipt` call, as `PreviewImportTransactions` is to `import-transactions`), `MatchReceipt`, `UnmatchReceipt`, `DeleteReceipt`, `ProposeReceiptMatches` (`propose-receipt-matches`), and the queries `FinanceReceipts` (`receipts`) and `FinanceReceipt` (`receipt`). Rationale: the plan's `AnnotateFinanceTransaction`, `RecordFinanceReceipt`, `MatchFinanceReceipt`, `UnmatchFinanceReceipt`, `DeleteFinanceReceipt` and `ProposeFinanceReceiptMatches` would have needed seven exceptions in both parity tests, and the CLI names the plan gives (`record-receipt`, `match-receipt`, `delete-receipt`) are exactly what the rule gives for the shorter names. Date: 2026-10-07.
- Decision: whether an annotation is the person's or the agent's is decided by the caller, not an argument: the API reads the audit principal, which is `agent` exactly when the agent's operations call (the finance tool), so the agent cannot claim to be the person. Manual matches are `person` from every surface, the agent's included: the agent matches by hand only when the person asks, behind a confirmation card. Date: 2026-10-07.
- Decision: `RecordReceipt` refuses a receipt whose lines do not add up unless `isUnbalancedAccepted` is true; the tool judges such a call a read (refused before the person is asked, as `import_transactions` does with rows that do not add up) and accepts the flag only "when the person says so". The receipt job, which has nobody to ask, records an unbalanced receipt marked `unbalanced` so the person sees it. Also refused: an item below zero, a discount above zero (a discount is negative, as printed), a discount of a line that is not an item, an unknown kind, and line, subtotal or total amounts with more places than the currency has. A unit price may have more places (1.599 per pound). Date: 2026-10-07.
- Decision: the check difference is the first total that misses: the items, discounts and fees against the subtotal when one is printed, else the subtotal (or those lines) with taxes and tips against the total; signed as what the lines come to less what is printed. Date: 2026-10-07.
- Decision: `ProposeReceiptMatches` takes a third argument, each candidate's account mask by finance account id, since a finance transaction does not carry its account's mask. The automatic match is the one exact-amount candidate, or, when several have the exact amount, the one on the card whose digits the receipt prints. Its confidence is 0.70, plus 0.15 for the same card and 0.15 for a merchant word in common, at most 1. A receipt with no day of purchase has no candidates. Merchant words are NFKC, lower case, three or more characters, not mostly digits, and not one every merchant uses (store, online, payment...). The matcher does not match a receipt the person has matched by hand. Date: 2026-10-07.
- Decision: a manual match with no amount explains the charge's amount or the receipt's total, whichever is less, so a split shipment matched without amounts still adds up per charge. Date: 2026-10-07.
- Decision: candidates come back as `ReceiptMatchCandidateView`, with the finance transaction itself (`financeTransaction`), so the dashboard can show a candidate without a second read. `RecordReceipt` answers `RecordedReceiptView` (the receipt, a sentence for the check, the candidates when the matcher left them, and whether it replaced an earlier read), `PreviewRecordReceipt` answers `ReceiptPreviewView`. `DeleteReceipt` answers a boolean, as `DeleteAsset` does. Date: 2026-10-07.
- Decision: the finance transaction an upload is the receipt for is kept on the upload itself, a nullable `agent_attachment.finance_transaction_id` (on delete set null), added by the receipts migration, which was first added as 0153 and renumbered 0154 when the branch was rebased onto `main` (unreleased, so amended in place rather than followed by a new migration; the forward, reverse and forward-again proof was run again). The receipt job's subject is the source alone. `ReadReceipt` takes `financeTransactionId` only with an upload: a stored message has nowhere to remember it, and its receipt is matched by the matcher, or by hand with `MatchReceipt`, once read. The tool's `read_receipt` therefore takes only `mailbox_item_id`. Date: 2026-10-07.

- Decision (second review): one receipt explains at most its total across all its charges. `checkReceiptMatchFits` locks the receipt's row and then the charge's (always in that order) and refuses a match whose amount with the receipt's matches to its other charges would exceed its total. A match by hand with no amount takes the less of what other receipts leave of the charge and what the receipt's other matches leave of its total, refused when the receipt has nothing left. ## Context and Orientation

TeaNode is a Go mail server with a per-person agent and a React dashboard; read `AGENTS.md` and `CONTRIBUTING.md` at the repository root first, and follow `CONTRIBUTING.md` for naming and comments. The naming rule that matters most here: a name says what it holds without its parent (no bare `state`, `status`, `type`, `count`, `value`; enum-valued fields carry the enum's name; booleans start with `is`, `has`; numbers carry units such as `Amount`), no abbreviations, and Go receivers are named `self`.

Finance lives in these places. `internal/models/finance.go` holds `FinanceTransaction` (amounts are decimal strings, negative is money out; enum types such as `CategorizedBy` and `DuplicateDecidedBy` live beside it). `internal/db/database_finance.go` holds the transaction table access (`agent_finance_transaction`), and `internal/db/database_budget.go` holds spending categories. Migrations are numbered SQL files in `internal/db/migrations/` with a `.reverse.sql` twin; the highest on main was `0153` when this branch was rebased, so this plan adds `0154`. Read `docs/coding/database-migrations.md` before writing one. `internal/finance/` holds pure logic (for example `transaction_rows.go`, which checks rows read off screenshots and is the closest model for the receipt check). `internal/agent/finance_statement.go` holds agent operations that write finance data inside a transaction and audit them. `internal/api/v1api/apigraph/agent_finance*.go` exposes them over GraphQL (fields are discovered by reflection from Go method signatures; follow the neighbors). `internal/client/finance.go` is the client the CLI uses, `internal/cmd/finance.go` the `teanode finance` commands, and `internal/agent/tools/finance/` the agent's finance tool, whose operations, argument descriptions, confirmation cards and risk levels are declared in `finance.go` there. `docs/subsystems/finance.md` describes all of it and `docs/reference/command-line.md` the CLI.

Mail sorting: `internal/agent/triage.go` sorts each new message into a category, one of which is `receipt` ("an order, an invoice, a payment, a booking confirmation"). Background work is queued as agent jobs: `AgentJobKind` values in `internal/models/agent.go` (for example `AgentJobCategorize`, run by `internal/agent/categorize.go` with the decision model). Each job kind needs a label (see `internal/models/agent_job_kind_labels_test.go` and `web/src/agentRuns.ts` `RUN_KINDS`).

Attachments: `internal/agent/attachment.go` defines `models.AgentAttachment` handling, `deleteAttachments`, and `scavengeAttachments`, which deletes attachments that were uploaded and never sent with a message (`ListOrphanAgentAttachments` in the db layer). `ExtractAttachmentText` turns a PDF or text file into text; `IsImageAttachment` tells a picture.

Dashboard: `web/src/pages/finance/financeTransactionDialog.tsx` is the transaction details dialog, `financeTransactions.tsx` the list, `financeApi.ts` the GraphQL documents and types. Follow `docs/coding/frontend-design.md`; errors and successes are toasts, never inline text in a card; data tables stay tables on a phone; buttons styled as links are refused by a lint check unless they say why. Strings go in `web/src/i18n/en.ts`, `ja.ts` and `zh.ts`.

Terms used below. A receipt is one merchant's printed or emailed record of one purchase or order. A receipt line is one printed line of it. Balanced means every line adds up to its total, to the cent, and, when a subtotal is printed, its item and discount lines come to it, with the fee lines or without them (see the Decision Log entry marked "end-to-end order email"). A match is a link between one receipt and one transaction with the amount of that transaction the receipt explains.


## Plan of Work

Milestone 1 adds the schema. Migration `0154_finance_receipts.sql` (and its reverse) adds to `agent_finance_transaction` the columns `annotation text NOT NULL DEFAULT ''` and `annotated_by text NOT NULL DEFAULT ''` (empty, `person` or `agent`), and creates three tables. `agent_finance_receipt` has `id`, `agent_id`, `receipt_source_kind` (`mail_item`, `gmail_message`, `attachment`), exactly one of `mail_item_id`, `gmail_message_id`, `agent_attachment_id` (a CHECK enforces that the one named by the kind is set and the others are null), `merchant_name`, `merchant_receipt_number`, `purchased_on date NULL`, `purchased_at timestamptz NULL`, `currency_code`, `subtotal_amount numeric(19,4)`, `total_amount numeric(19,4)`, `payment_account_mask`, `receipt_check_state` (`balanced`, `unbalanced`), `check_difference_amount numeric(19,4)`, `created_at`, `modified_at`, with a unique index on the agent and the source (so reading the same email again replaces its receipt). `agent_finance_receipt_line` has `id`, `agent_id`, `receipt_id` (cascade), `line_number`, `receipt_line_kind` (`item`, `discount`, `tax`, `fee`, `tip`), `description`, `quantity numeric NULL`, `quantity_unit`, `unit_price_amount numeric(19,4) NULL`, `line_amount numeric(19,4)` signed as printed (discounts negative), `tax_class_code` (the receipt's own mark: on an item or discount the tax it falls under, on a tax line the mark it covers; empty when the receipt does not say), `discounted_line_id NULL` (a discount's item), and `spending_category_id NULL` (reserved for the later split; always null in this plan). `agent_finance_receipt_match` has `receipt_id` and `finance_transaction_id` as its key (both cascade), `matched_amount numeric(19,4)`, `receipt_match_source` (`receipt_matcher`, `person`), `match_confidence numeric NULL`, `created_at`. Models go in `internal/models/finance.go`: `FinanceReceipt` (with its `Lines` and `Matches`), `FinanceReceiptLine`, `FinanceReceiptMatch`, the enums `ReceiptSourceKind`, `ReceiptLineKind`, `ReceiptCheckState`, `ReceiptMatchSource`, `AnnotatedBy`, and `Annotation`/`AnnotatedBy` on `FinanceTransaction`. The db layer gains: setting a transaction's annotation; upserting a receipt with its lines (replacing lines on a second read of the same source); getting, listing (by transaction, by date range, unmatched) and deleting receipts; adding and removing matches; and listing a transaction's receipts. Every write that a person or agent makes is audited like the other finance writes (`models.AuditResource...`; add `AuditResourceFinanceReceipt`). `ListOrphanAgentAttachments` must leave out attachments a receipt points at, and deleting a receipt deletes its attachment unless a message also holds it. Database tests prove each of these, the CHECK, the cascade, and that the scavenger keeps a receipt's photo.

Milestone 2 adds the logic and the surfaces. In `internal/finance/receipt.go`, `CheckReceipt` computes `receipt_check_state` and the difference exactly in minor units (follow how `transaction_rows.go` does money), normalizes descriptions with the same NFKC normalization, refuses lines with an unknown kind, a negative item, a discount pointing at a line that is not an item, or amounts with more places than the currency has. `MatchReceipt` proposes matches for a receipt against the agent's transactions: candidates are money-out transactions in the receipt's currency posted from three days before to seven days after `purchased_on`, not mirrored duplicates, preferring the same account mask when the receipt shows one and a merchant name that shares a word with the transaction's description or merchant name. An exact amount match that is the only candidate is matched automatically with confidence; anything else is returned as candidates and left unmatched, never guessed. It must never remove or replace a match whose source is `person`. Agent operations in `internal/agent/finance_receipt.go`: annotate a transaction (with the person rule from the Decision Log), record a receipt (check, upsert, then match), match and unmatch by hand (source `person`), delete a receipt, list and get receipts, and propose matches. GraphQL (`internal/api/v1api/apigraph/agent_finance_receipt.go`): `AnnotateFinanceTransaction`, `RecordFinanceReceipt`, `MatchFinanceReceipt`, `UnmatchFinanceReceipt`, `DeleteFinanceReceipt`, `FinanceReceipts`, `FinanceReceipt`, `ProposeFinanceReceiptMatches`, plus `annotation`, `annotatedBy` and the receipt count on transactions. The client and CLI mirror them: `teanode finance annotate <transaction-id> <text>`, `teanode finance receipts`, `receipt <id>`, `record-receipt <file.json>` (with `--dry-run`, which checks and proposes matches without writing), `match-receipt`, `unmatch-receipt`, `delete-receipt`. The finance tool gains the same operations with clear argument descriptions telling the model how to read a receipt (one line per printed line, as printed, discounts negative, taxes as their own lines with their marks, "You Saved" lines left out) and that a receipt that does not balance is refused unless the person confirms. Reading and listing are reads; annotating, recording and matching are changes; deleting asks. Tests cover the check (a real-shaped grocery receipt with two tax classes and promotions balances; a misread line is reported as unbalanced by its difference), matching (exact unique match, ambiguity left unmatched, a person match survives re-matching, split shipments matched by hand with amounts), the annotation rule, the API, the CLI and the tool.

Milestone 3 adds the background job. A new job kind `AgentJobReadReceipt` (label "Read a receipt") runs `internal/agent/receipt_job.go`. It is enqueued when triage sorts a TeaNode mail item as `receipt`, and when a person uploads a receipt photo or PDF to a transaction from the dashboard or CLI. It reads the source (the mail item's text, the PDF's extracted text, or the picture shown to a model that accepts pictures; choose the configured model the way other picture-reading code does, and skip pictures with a clear note in the run when no such model is configured), asks the model for the receipt as structured JSON in the shape `RecordFinanceReceipt` takes, records it through the same agent operation as Milestone 2 (so the same check and matching apply), and writes a one-line run title saying what it read and what it matched. A message that turns out not to be a purchase (a shipping notice with no amounts, a marketing email) records nothing. Running it twice on the same message replaces, never duplicates. Gmail messages are read by the agent through the Gmail skill and recorded with the tool; no Gmail polling is added here. Tests drive the job with a fake model answer and prove the record and match.
