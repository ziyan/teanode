# Reading mail in the dark

## Why this matters

The dashboard has a dark theme and honours the system one. A message rendered
inside it does not: `buildDocument` in `web/src/pages/mailDetail.tsx` writes
`background:#fff;color:#16161a` into the frame's stylesheet, so every message
opens as a white rectangle in the middle of a dark page. At night that is the
brightest thing on the screen, and it is the thing you were trying to read.

After this change, a message opened in the dark theme is dark: plain messages
render on the dashboard's own dark ground, and a message that paints itself
light can be darkened with one control that remembers what you chose.

You can see it working by setting the theme to dark and opening two messages —
a plain one, which is simply dark, and a marketing one, which is still as its
sender drew it until you press the control.

## What makes this harder than it sounds

A message carries its own colours. Roughly three kinds arrive:

1. **No colours of its own.** A forwarded note, a bug tracker, anything
   composed as plain HTML. It inherits whatever the frame sets, so setting a
   dark ground and light text is enough and looks right.
2. **Colours on the text but not the ground**, which is the dangerous one. A
   message that says `color:#333` and nothing else, rendered on a dark ground,
   is dark grey on near-black. Unreadable — and *worse* than the bright
   rectangle, because at least that could be read.
3. **Fully painted**, table backgrounds and all: most marketing mail. It
   ignores anything the frame sets, so it stays bright whatever we do to the
   defaults.

So "just set the background dark" fixes (1), breaks (2), and does nothing for
(3), which is most of the mail anybody actually complains about. Any approach
that recolours a message is guessing at somebody else's design, and will
sometimes be wrong. The reader has to be able to say "no, as sent".

## What this does

Two mechanisms, because the three kinds above need two different answers.

**A dark ground, when the dashboard is dark.** The frame's stylesheet sets
`color-scheme: dark` and a dark background with light text, taken from the
dashboard's own tokens rather than invented. This fixes kind (1) completely
and costs nothing for kind (3), which overrides it anyway.

Kind (2) is the reason the text colour is set as a *default* the message can
override — which it does, by definition, since it sets `color`. A message that
sets a colour and no ground is left on the light ground: see the decision
below.

**A control that darkens anything.** Above the frame, two choices — *As sent*
and *Dark* — which set a filter on the whole document:

    filter: invert(1) hue-rotate(180deg)

with images, video and anything with a background image inverted back, so
photographs and logos look normal. This is the transform every mail client
that offers this uses, because it is the only one that darkens a document it
does not understand while keeping hues recognisable. It is imperfect on
gradients and on shadows, which is why it is a button and not the default.

The choice is remembered in `localStorage`, per reader, not per message:
somebody who wants dark mail wants it for the next message too.

## Where the code is

- `web/src/pages/mailDetail.tsx` — `buildDocument(html, mailId)` builds the
  whole document that goes into the frame, including its stylesheet and its
  Content-Security-Policy. This is where the colours are decided. The rendered
  tab is around line 215.
- `web/src/components/messageFrame.tsx` — the sandboxed iframe. It measures
  `#teanode-content` to size itself; nothing here needs to change, but the
  wrapper it measures is the element the filter goes on.
- `web/src/components/theme.tsx` — `useTheme()` returns `system | light |
  dark`. `system` has to be resolved against
  `matchMedia('(prefers-color-scheme: dark)')` to know what is actually on
  screen.
- `web/src/style.css` — the dashboard's tokens. The frame cannot use `var()`
  from the parent document, so the two colours have to be written into the
  frame's stylesheet as literals; take them from the dark palette at the top
  of the file so they match rather than approximate.

The frame's CSP is `default-src 'none'; img-src data: 'self'; style-src
'unsafe-inline'; font-src data:`. A filter is a style, so nothing about the
policy changes.

## Milestone one: the frame follows the theme

At the end of this milestone a plain HTML message opens dark in the dark theme
and unchanged in the light one.

`buildDocument` takes the resolved theme as an argument rather than reading it
itself, so it stays a pure function of its inputs and the caller decides. In
dark it emits `color-scheme:dark`, the dark ground and the light text; in
light it emits exactly what it emits today.

The caller is the `useMemo` at line 90 of `mailDetail.tsx`, whose dependencies
gain the theme so a message re-renders when the reader switches.

Acceptance. `cd web && npm run build`. Open a plain-HTML message with the
theme set to dark: it is dark, and the text is legible. Switch the theme to
light with the message open: it turns light without a reload. Open a marketing
message: it is unchanged, because it paints its own ground.

## Milestone two: the control

At the end of this milestone any message can be darkened.

Add `As sent` / `Dark` above the frame, in the rendered tab only, shown only
when the dashboard is dark — in the light theme there is nothing to fix and
the control would be a question nobody asked.

`Dark` adds a class to `#teanode-content` inside the frame's stylesheet:

    .dark-filter{filter:invert(1) hue-rotate(180deg)}
    .dark-filter img,.dark-filter video{filter:invert(1) hue-rotate(180deg)}

The choice lives in `localStorage` under a key beside the theme's, read the
way `storedTheme()` reads its own — inside a `try`, because a browser in
private mode refuses storage and that is not a reason for the page to fail.

Acceptance. Open a marketing message in the dark theme: it is bright, and
pressing `Dark` darkens it with its photographs still looking like
photographs. Reload: it is still dark. Press `As sent`: it is bright again,
and stays that way for the next message.

## Milestone three: the other tabs

At the end of this milestone nothing else on the page is bright.

The text, HTML-source and headers tabs render through `.message-text` and
`HighlightedHtml`, which are the dashboard's own markup and already themed —
verify rather than assume, especially the syntax highlighting, whose token
colours were chosen against a light ground and may be unreadable on a dark
one.

Acceptance. Each tab of the same message, in the dark theme, read end to end.

## Decisions

**A message that sets a text colour and no ground stays on the light ground.**
This is the case that cannot be got right by guessing. Detecting it means
parsing the message's CSS, and being wrong means dark grey on black — text
that cannot be read at all, which is worse than text that is too bright. The
control is the answer for these: the reader can see the message is unreadable
and press the button.

**A filter rather than recolouring.** Rewriting a message's colours means
understanding its design well enough to substitute for it, on documents built
by every mail tool there is. The filter is honest about what it is: a
reversible transform of the whole thing, not an interpretation.

**Remembered per reader, not per message.** Per message would be more precise
and would mean pressing it again on every message, which is what the reader is
complaining about.

## Still open

Whether the dark ground should apply in the `system` theme when the system is
dark. It should — that is what `system` means — but it needs the media query
resolved in JavaScript rather than in CSS, because the frame's document is
built as a string. Milestone one has to handle it; noted here because getting
it wrong shows up only for readers who never set the theme explicitly, which
is most of them.
