# The primary conversation on Telegram and Discord

This ExecPlan is a living document. The sections `Progress`, `Surprises &
Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up
to date as work proceeds. It follows the ExecPlan format described in

## Purpose / Big Picture

A person talks to their agent in the dashboard's drawer, from the command
line, and from the browser extension. The place they already have open all
day is a chat app. After this change a person can make a bot of their own
in Telegram or Discord, hand its token to their agent on the agent page,
link the chat with a code the page shows, and from then on talk to the
same primary conversation from that chat: the agent shows it is typing,
streams its answer into a message it keeps editing, sends back what it
made (a chart, a file), takes files and photos sent to it, asks for a yes
on the same confirmation cards the drawer shows, and answers a handful of
slash commands. Nothing an operator has to set up: the bot is the
person's, and only the chat they linked reaches the agent.

Observable outcome: on the agent page, under "Chat apps", paste a Telegram
bot token; the card shows the bot's name and a six-character code; in
Telegram, send `/link ABC123` to the bot; it answers "Linked."; send "what
needs me today?" and the bot types, then answers with what the drawer
would have said; send a photo with "what is this?" and it describes it;
ask it to make a chart and the chart arrives as a file; ask it to delete
a message and it asks "yes or no?" first.

## Surprises & Discoveries

- Observation: the help text says "start a fresh primary conversation",
  and the end-to-end test that waited for the `/new` reply matched the
  help sent at link time instead; the assertion then ran before `/new`
  was handled.
  Evidence: `channel_test.go` failing with "1 main, 0 named" on the first
  run; fixed by waiting for the reply's own words.

## Decision Log

- Decision: the bot is the person's, configured on their agent page, not
  the operator's in the server configuration.
  Rationale: this is a personal agent; a shared operator bot would need a
  directory of who is who, and a person's own bot needs only their token
  and a code to link the chat. The operator keeps a switch
  (`agent.features.chatApps`).
  Date/Author: 2026-09-11, Claude with the owner.
- Decision: the Telegram and Discord clients are written here over
  `net/http` and the vendored websocket library, not taken from a
  library.
  Rationale: the same choice as for the model providers, the connected
  servers and the browser: a thin client the tests can drive against a
  fake, no third-party code in the build for a few HTTP calls and one
  websocket.
  Date/Author: 2026-09-11, Claude.
- Decision: of several server instances sharing one database, exactly one
  runs a given bot: the channel row carries a claim (`claimed_by`,
  `claimed_until`) an instance takes when nobody holds it or the holder's
  claim has lapsed, renews every thirty seconds while its bot runs for
  ninety seconds at a time, and releases when it stops; an instance that
  finds its claim gone stops its bot.
  Rationale: Telegram's polling refuses a second poller on the same token
  and Discord's gateway drops a second session; the job queue claims its
  rows the same way, and the owner reminded that the server runs in more
  than one instance.
  Date/Author: 2026-09-11, Claude with the owner.
- Decision: no message bus between instances for now. A change to a
  channel row reaches the instance running its bot within a tick (thirty
  seconds) through the row's modified time; a card is answered on the
  instance whose bot asked it. What would need one is forwarding an
  answer given in the drawer to the chat, which the reference did and
  this does not yet; the owner offered Redis as the backbone for that,
  and it is the way to go when that is wanted.
  Rationale: the database already carries the one shared fact (who runs
  what); a bus for a thirty-second lag is not worth a dependency.
  Date/Author: 2026-09-11, Claude with the owner.
- Decision: a turn's events cross instances as PostgreSQL notifications,
  not over Redis. The database already has a LISTEN connection for the
  folder changes; an event is a word to whoever listens now, not a fact
  to keep, and losing one costs a transcript read the drawer does anyway
  when the turn ends. The words back — stop, an answer, a decision on a
  card — travel the same way on a second channel, and the instance
  running the turn applies them; the pieces of an answer are joined
  before they travel so a fast model is not a notification per word.
  Redis is not needed for any of this.
  Rationale: one shared mechanism the deployment already runs, no new
  dependency, and the payload limit (about eight kilobytes) is enough for
  what a drawer draws live, the rest arriving with the transcript.
  Date/Author: 2026-09-11, Claude with the owner.
- Decision: a page the agent made reaches a chat app as a link, signed
  with the server's secret, naming the one artifact and expiring after
  thirty days, opening without a sign-in.
  Rationale: Telegram and Discord show an attached HTML file as a
  download and never run its script, so a chart in it is blank; the
  person taps a link in their own chat and sees it drawn. The link grants
  that one page and nothing else, and a chat is theirs (or a group they
  chose to ask in).
  Date/Author: 2026-09-11, Claude with the owner.
- Decision: a chat is linked with a code the agent page shows, sent to the
  bot as `/link CODE`; until then the bot answers only with how to link.
  Rationale: a bot token found by somebody else must not give them the
  agent; the code is on a page only the person can see.
  Date/Author: 2026-09-11, Claude.

## Outcomes & Retrospective

Done 2026-09-11, uncommitted with the rest of the branch. A person's own
Telegram or Discord bot carries their primary conversation: the same
turn, the same cards, typing and a streamed preview, files both ways, a
handful of commands; one instance runs each bot by a claim on its row.
The clients are two small packages over `net/http` and the vendored
websocket library, each tested against a fake of the app.

What held up: `Agent.Ask` and its events were enough for a third surface
— the chat turn is a subscriber like the drawer and the terminal, with a
preview message where they have a transcript. What was learned: a help
text that repeats a command's words is a trap for a test that waits for
words; the reference's "forward what was answered elsewhere" needs a
bus between instances, which this leaves for Redis when it is wanted.

Left open: telling the chat that a card it asked was answered from the
drawer (the turn goes on either way; the chat's "reply yes or no" just
stays); `/compact` from the chat; Discord's own slash commands
(application commands) rather than text ones; a real Discord bot in the
owner's hands. The owner's real Telegram bot works, and was what showed
the drawer standing still.

## Context and Orientation

The personal agent lives in `internal/agent/`; a turn is started with
`Agent.Ask(&AskSettings{...})` (`internal/agent/ask.go`) and streams
`Event`s (`text`, `message`, `tool_call`, `tool_result`, `confirmation`,
`question`, `note`, `done`, `error`) to subscribers; the command line
client (`internal/cmd/agent_chat.go`) and the drawer follow them. A
confirmation is resolved by `ResolveAgentConfirmation` and a question by
the same mechanism the drawer uses (`internal/api/v1api/apigraph/
agent_ask.go`); a run is stopped by `StopAgentRun`. Files that come with a
turn are `AgentAttachment` rows (`internal/api/v1api/apigraph/
agent_attachment.go` shows how one is created from an upload, with
`agent.ExtractAttachmentText`) and are handed to `AskSettings.Attachments`;
what the agent makes for the person are attachments with the message id
`artifact`. Per-agent secrets are sealed with the server secret
(`Agent.SealSecret`, `OpenSecret` in `internal/agent/tools_mcp.go`) and
kept in the database. The agent page is `web/src/pages/agent.tsx`, built
from `SettingsSection` cards, each with its own Save; the operator's
feature switches are in `internal/config/agent.go` (`AgentFeatures`).

Telegram's Bot API is plain HTTPS: `getMe`, `getUpdates` with a long-poll
timeout, `sendMessage`, `editMessageText`, `deleteMessage`,
`sendChatAction` (typing shows for five seconds), `getFile` and a download
address, `sendDocument` and `sendPhoto` as multipart, `setMyCommands`; a
message is at most 4096 characters; a 429 carries `retry_after`.
Discord's gateway is a websocket: `hello` gives the heartbeat interval,
the client sends `identify` with its token and intents (direct messages,
guild messages, message content), then receives `MESSAGE_CREATE` events;
`heartbeat` on the interval, `resume` after a drop; its REST is HTTPS
with a `Bot` token: create and edit a message (2000 characters at most),
trigger typing (shows for ten seconds), upload a file as multipart;
attachments on a message carry public download addresses.

## Plan of Work

### Milestone 1 — storage, API, the page, the command line

Migration `0042_agent_channel.sql` (and its reverse): `agent_channel`
(id, agent_id → agent on delete cascade, kind `telegram`|`discord`, token
sealed, bot_name, linked_id (a Telegram chat id or a Discord user id),
link_code, enabled, last_error, last_seen_at, created_at, updated_at;
unique on agent_id and kind). `models.AgentChannel`; `db` methods
`ListAgentChannels(agentId)`, `ListEnabledAgentChannels()`,
`PutAgentChannel`, `DeleteAgentChannel`. API in `apigraph/agent_channel.go`:
`ListAgentChannels` (never the token; `hasToken`), `SetAgentChannel(kind,
token?, enabled?)` — a new token is sealed and a new link code drawn,
`RemoveAgentChannel(kind)`, `UnlinkAgentChannel(kind)` (a new code). The
feature switch `chatApps`. The page: a "Chat apps" card with one row per
kind: the token (write-only, "set" once it is), the bot's name once seen,
the code and how to send it, "Linked to …" with Unlink, a switch, Remove.
CLI `teanode agent channel list|set --kind telegram --token -|remove|unlink`.

### Milestone 2 — Telegram and the shared turn

`internal/channel/telegram/client.go`: a client over `net/http` with the
calls above and a poller that hands each update to a function; tested
against `httptest`. `internal/channel/channel.go`: the manager — started
and stopped with the agent worker, it lists enabled channels every
minute and on a change notice, starts a bot per row, stops one whose row
went — and the turn, shared by both apps through a small interface
(`Chat`: send, edit, delete, typing, send file, the linked id and the
name). The turn: an incoming message from the linked chat starts
`Agent.Ask` on the main conversation with surface `telegram` or
`discord`; a typing action every four seconds while the run lasts; the
streamed text edited into one preview message at most once a second and
never past the app's limit; on `message`, the final text replaces the
preview, chunked at the limit on a line break, with Markdown tried and
plain text as the fallback; on `confirmation`, a message with the card's
words and "reply yes or no", and the next message from the chat resolves
it; on `question`, the question and its choices, and the next message
answers it; on `done`, the attachments the run made are sent as files
(photos as photos); on `error`, the error in words. Files and photos in
a message are downloaded and made attachments of the turn. An unlinked
chat gets the link instructions; `/link CODE` links it; the commands
`/new` (a fresh primary conversation, the old one kept), `/stop`,
`/status`, `/compact`, `/help`, `/unlink`, and `/start` (a greeting and
the help); in a group, only a reply to the bot or a message starting with
`/ask` is a turn. The prompt's `<surface>` overlay says "a chat app:
short, plain text, no tables".

### Milestone 3 — Discord

`internal/channel/discord/client.go`: the gateway over the vendored
websocket library (hello, identify with intents, heartbeat, resume after
a drop, `MESSAGE_CREATE` handed to a function) and the REST calls; tested
against a fake gateway and `httptest`. A message from the linked user in
a direct message, or mentioning the bot in a channel, is a turn; the
rest is the shared turn.

### Milestone 4 — docs and checks

`docs/reference/command-line.md`, `docs/configuration.md` (the switch), a
section in the agent page's help, the changelog; `make lint-ci`,
`make test`; a real Telegram bot of the owner's on the dev server.

## Validation and Acceptance

Unit tests: the Telegram client against `httptest` (updates polled,

Discord gateway against a fake websocket (identify sent after hello,
heartbeats on the interval, a message event delivered, a resume after a

(`internal/agent/ask_test.go`'s `fakeModel`): typing sent, a preview
edited, the final answer chunked, a confirmation resolved by "yes", a
photo made an attachment, `/link` with the right and the wrong code,
`/new` and `/stop`. End to end: the Purpose's scenario with a real bot.

## Idempotence and Recovery

The migration has a reverse; a bot that fails to connect records
`last_error` on its row and is retried each minute; a token replaced
re-draws the link code and drops the link. Removing the row stops the
bot.
