# Skills: installing tools from a signed registry

This ExecPlan is a living document. The sections `Progress`, `Surprises &
Discoveries`, `Decision Log` and `Outcomes & Retrospective` must be kept up to
date as work proceeds. It is maintained in accordance with `~/.claude/PLAN.md`;
this repository has no `PLANS.md` of its own.

## Purpose / Big Picture

Today the only way to give the agent a new tool is to write Go and ship a
release. After this change, an operator runs

    teanode agent skill install weather

and within a moment the agent has a `get_weather` tool it did not have before,
fetched from a public registry, checked against a signature this server ships
with, and offered to everybody on the server under the ordinary tool policy.
Asking the agent "what is the weather in Alpharetta" now answers from the
National Weather Service rather than saying it cannot.

A **skill** is a single Markdown file with a YAML header that declares one or
more tools. Each declared tool says what it is called, what it does, what
parameters it takes, and how to carry it out: by making HTTP requests, by
running a command, or by a short sequence of those steps feeding one another.
Nothing in a skill is Go code, and nothing in it is executed as code by this
server; it is read as data and carried out by an interpreter written here.

Two things make this safe enough to do at all. The registry publishes an index
that is **signed**: each entry carries an Ed25519 signature over the skill's
name, version, address and content hash, made by a key whose public half ships
inside this server's binary. A skill whose signature or hash does not check out
is refused before a line of it is read. And a skill's **shell steps never run
on this server**: they are carried to the person's own attached computer, the
same way the `shell` and `filesystem` tools already reach it, so a hostile
skill that got past the signature still cannot touch the mail server.

You can see the whole thing working, end to end, at the end of Milestone 5:
install the weather skill, ask the agent about the weather in a US town, and
watch it call `skill__weather__get_weather` and answer with a real forecast.

## Orientation: where everything in this plan lives

A reader new to this repository needs five landmarks.

`internal/agent/` is the agent: the loop that runs a turn (`ask.go`), the
worker that runs jobs with nobody watching (`agent.go`), and the adapters that
turn outside things into tools. `internal/agent/tools/` is the tool catalog:
`tool.go` defines what a tool is, and every tool lives in a package of its own
beside it, registering itself from an `init` function. `internal/agent/tools/
all/all.go` imports them all, and is the file you add a new tool package to.

`internal/agent/tools_mcp.go` is the closest existing thing to what this plan
builds: it takes tools that are discovered at runtime from a connected server
rather than compiled in, gives them names of the shape `mcp__<server>__<tool>`,
and hands them to the catalog. Read it before starting Milestone 4; the skill
adapter is the same idea with a different source.

`internal/db/` is storage. Every table has a migration under
`internal/db/migrations/`, numbered, each with a matching `.reverse.sql`.
Tables are named in the singular (`agent`, `agent_job`, `agent_memory`), and
the newest migration at the time of writing is `0044_agent_memory_embedding.sql`;
this plan adds `0045`.

`internal/api/v1api/apigraph/` is the API. Operations are plain Go methods on
`*graph` whose names become the GraphQL operation names by reflection, and
permissions are checked with `self.requirePermission(ctx, ...)`.
`internal/cmd/` is the `teanode` command line, and `web/src/` the dashboard.

`internal/computer/` is the program a person runs on their own machine
(`teanode computer start`), and `internal/agent/tools/computer/` is the pair of
tools that reach it. `computer.Of(run, name)` returns the attached computer a
call means, or an error explaining why there is none; `attached.Ask(ctx,
"shell", arguments, wait)` runs a command there. `internal/agent/tools/coding/
coding.go` is a short, complete example of a tool built on that pair, including
how to quote a command safely; read it before Milestone 3.

## What a skill file looks like

A skill is Markdown with a YAML header fenced by `---` lines. The header is the
whole of what this server reads; the prose below it is for a person.

    ---
    name: weather
    description: Weather forecast via the National Weather Service API
    tools:
      - name: get_weather
        description: Get the weather forecast for a US location.
        type: workflow
        timeout: 30
        parameters:
          type: object
          properties:
            location:
              type: string
              description: "A town, for example 'Alpharetta, GA'"
          required: ["location"]
        steps:
          - name: geocode
            type: http
            method: GET
            url: "https://nominatim.openstreetmap.org/search?q={{location}}&format=json&limit=1"
            headers:
              Accept: application/json
            result: json
            select:
              lat: "0.lat"
              lon: "0.lon"
          - name: forecast
            type: http
            method: GET
            url: "https://api.weather.gov/points/{{steps.geocode.lat}},{{steps.geocode.lon}}"
            result: json
            select:
              summary: "properties.periods[0].shortForecast"
    ---

    Whatever prose the author wants, ignored by this server.

The pieces, each defined here because none of them is ordinary English:

**`name`** is the skill's name, which namespaces its tools. **`description`**
is a sentence for a person reading a list of skills.

**`tools`** is the list of tools the skill declares. Each has a **`name`**,
which must be lower-case words joined by underscores; a **`description`**,
which is what the model reads to decide whether to call it, and so is the most
important line in the file; **`parameters`**, which is a JSON Schema object
exactly as the existing tools write it (see `tools.Object` in
`internal/agent/tools/tool.go`); an optional **`timeout`** in seconds; and a
**`type`** which is one of three words.

**`type: http`** means the tool is one HTTP request. It carries `method`,
`url`, optional `headers`, an optional `body`, `result` (`json` or `text`), an
optional `maxBytes`, and an optional `select`.

**`type: shell`** means the tool runs a command. It carries `command`, a list
of strings where the first is the program and the rest its arguments. It is
never a single string to be handed to a shell, because that invites quoting
bugs; the list is quoted by this server before it travels.

**`type: workflow`** means the tool is a sequence of **`steps`**, each of which
is itself an `http` or `shell` step with a `name`. A later step may use what an
earlier one produced.

**Templating** is the `{{...}}` notation. `{{location}}` is the value of the
tool's own parameter of that name. `{{steps.geocode.lat}}` is the value named
`lat` that the step called `geocode` selected. Nothing else is understood: no
expressions, no function calls, no arithmetic. A reference to something that
does not exist is an error naming it, not an empty string, because a silently
empty URL is how a skill quietly fetches the wrong thing.

**`select`** turns a JSON answer into named values. Each entry is a name and a
path: dot-separated keys, with `[n]` or a bare number for an array index, so
`properties.periods[0].shortForecast` and `0.lat` both work. A path that
matches nothing yields no value, and a later `{{steps.x.y}}` referring to it is
the error described above.

**`result: json`** parses the answer and makes `select` possible.
**`result: text`** keeps it as text, and then the whole text is the step's
value under the name `text`.

## The registry and how a skill is trusted

The registry is a Git repository published over HTTPS. This plan pins the one
at `github.com/teanode/teanode-skills`, whose index is at

    https://raw.githubusercontent.com/teanode/teanode-skills/main/index.json

The index looks like this, abbreviated to one entry:

    {
      "publisher": "github.com/teanode/teanode-skills",
      "skills": [
        {
          "name": "git",
          "description": "Git repository operations",
          "version": "1.0.0",
          "url": "https://raw.githubusercontent.com/teanode/teanode-skills/main/skills/git/skill.md",
          "sha256": "1af06ee3e2a6d7b7cc10b4fd78cab7275bead3d12109c199cea408445958323d",
          "signature": "8jB2ZH59RxFV73BRZEpETp5ELJthTqpu6gndgqiAgKoo5OPQtu1iOkUBEC+R9rLyYMR98M/cQbmA6jr4o6auBA==",
          "tags": ["git", "repo", "shell"]
        }
      ]
    }

Verification has two halves and both are mandatory.

The **signature** is Ed25519, base64 encoded in the standard alphabet with
padding. The message signed is exactly

    name + "\n" + version + "\n" + url + "\n" + lowercase(sha256)

with no trailing newline. The public key is published by the registry at
its `keys` directory as a PEM document of type `PUBLIC
KEY`, which is an X.509 SubjectPublicKeyInfo wrapper around the 32 raw bytes.
**Do not fetch the key at runtime**: a key fetched from the same place as the
thing it vouches for proves nothing. Embed the 32 raw bytes in the binary with
`//go:embed` from a file committed at `internal/skills/keys/
teanode-skills-ed25519-public.pem`, and parse it with
`x509.ParsePKIXPublicKey`. Fetch the key file once, by hand, while implementing
Milestone 1, and record its SHA-256 in the Decision Log so a later reader can
tell whether it ever changed.

The **hash** is SHA-256 of the skill file's bytes exactly as downloaded, hex
encoded in lower case. It is checked after download and before the file is
parsed or stored. A mismatch is an error naming both hashes.

A skill that fails either check is refused, is not stored, and leaves whatever
was installed before untouched.

## Where a skill's steps run

An `http` step is made by this server, through `internal/util/safefetch`, which
is the same guard the `web_fetch` tool uses: it refuses private and loopback
addresses, so a skill cannot use the mail server as a way into the network it
sits in. Follow what `web_fetch` does rather than writing a new HTTP client.

A `shell` step is **carried to the person's attached computer** and run there,
through `computer.Of` and `attached.Ask(ctx, "shell", ...)`. It is never run on
this server. The consequences, which must be stated in the tool's own
description so the model plans around them: a skill with a shell step needs a
computer attached, is refused in a run with nobody present, and shows the
person a confirmation card before it runs.

## Storage and scope

A skill is installed by an operator and belongs to the server, not to a person.
Installing requires `server:manage`, the same permission that changes settings
and declares a connected server. Every person's agent is then offered the
skill's tools, subject to the ordinary tool policy: an operator can switch off
the whole `skills` family or a single tool by name in `agent.tools.disabled`,
and can raise any of them to require confirmation in `agent.tools.confirm`.

One table, `agent_skill`, in migration `0045_agent_skill.sql` with its reverse:

    CREATE TABLE "agent_skill" (
        "name"        varchar(64)  NOT NULL,
        "created_at"  timestamptz  NOT NULL,
        "modified_at" timestamptz  NOT NULL,
        "version"     varchar(32)  NOT NULL DEFAULT '',
        "publisher"   varchar(200) NOT NULL DEFAULT '',
        "url"         text         NOT NULL DEFAULT '',
        "sha256"      varchar(64)  NOT NULL DEFAULT '',
        "description" text         NOT NULL DEFAULT '',
        "content"     text         NOT NULL,
        "enabled"     boolean      NOT NULL DEFAULT true,
        PRIMARY KEY ("name")
    );

The file's whole text is stored in `content`, so a server that can no longer
reach the registry still has everything it needs, and so an operator can read
exactly what is installed. The reverse migration is `DROP TABLE IF EXISTS
"agent_skill";`.

## Milestones

### Milestone 1: the registry, verified

Create `internal/skills/` with `registry.go` and the embedded key. It offers
three things: `Index(ctx)` fetching and parsing the index; `Verify(entry)`
checking the signature against the embedded key; and `Download(ctx, entry)`
fetching the skill file and checking its hash. Nothing here touches the
database or the agent.

Fetch the public key by hand and commit it under `internal/skills/keys/`.

Write `registry_test.go` against an `httptest` server, never the network. Sign
a test entry with a key the test generates so the happy path is provable, and
assert that a tampered signature, a tampered hash, and a wrong name are each
refused with an error naming what failed. Add one test that the embedded
production key parses and is 32 bytes.

Acceptance: `go test ./internal/skills/` passes, and a small throwaway program
(or a test guarded by `testing.Short`) can fetch the real index and verify
every entry in it.

### Milestone 2: reading a skill file

Add `skill.go` to `internal/skills/`: a `Skill` type and `Parse(content
[]byte) (*Skill, error)` that splits the YAML header from the prose and reads
it with `gopkg.in/yaml.v3`, which is already vendored.

Validation is part of parsing and must be strict, because everything after
this point trusts the result: a name that is lower-case words and underscores;
at least one tool; each tool's name unique within the skill and of the same
shape; a `type` that is one of the three words; `parameters` present and an
object; `command` non-empty for a shell tool and a list, never a string; a
workflow having at least one step, each step named uniquely, each step's type
being `http` or `shell`. Any `{{...}}` reference is checked at parse time
against the tool's parameters and the names of earlier steps, so a skill that
refers to a step that does not exist is refused at install rather than failing
on first use.

Acceptance: `skill_test.go` parses the four real skills from the registry
(committed as fixtures under `internal/skills/testdata/`) and rejects a dozen
malformed ones, each with an error naming the problem.

### Milestone 3: carrying one step out

Add `run.go`: an interpreter that carries out one tool of a parsed skill given
its arguments. Templating, `select`, `result`, `maxBytes` and `timeout` all
live here, as does the sequencing of a workflow's steps.

HTTP goes through `safefetch`. Shell is built as a quoted command line exactly
as `internal/agent/tools/coding/coding.go` does it — reuse that quoting by
moving it into `internal/agent/tools/` as a shared helper rather than writing
it twice — and handed to an interface the caller supplies, so this package
stays testable without an attached computer:

    type Shell interface {
        Run(ctx context.Context, command string, timeout time.Duration) (stdout string, exitCode int, err error)
    }

A nil `Shell` means shell steps are refused with an error saying a computer
must be attached.

Bound everything: at most 10 steps in a workflow, at most 30 seconds per step
unless the tool says otherwise and never more than 120, at most 256 KiB read
from any HTTP answer unless `maxBytes` says less.

Acceptance: `run_test.go` carries out the weather skill's workflow against an
`httptest` server standing in for both services and gets the expected values;
carries out a shell tool against a fake `Shell` and asserts the command was
quoted; and proves a missing `{{steps.x.y}}` is an error naming `x.y`.

### Milestone 4: skills become tools

Add `internal/agent/tools_skill.go`, modelled on `tools_mcp.go`. It reads the
installed skills, parses each, and builds one `*tools.Tool` per declared tool,
named `skill__<skill>__<tool>`, in a new family `skills`.

Add `FamilySkills Family = "skills"` to `internal/agent/tools/tool.go` and
`"skills"` to `config.AgentToolFamilies` in `internal/config/agent.go`. There
is a test in `internal/agent/tools/tools_test.go`
(`TestEveryFamilyIsAPolicyName`) that holds those two lists together; it will
fail until both are updated, which is the point of it.

Risk: a tool with only `http` steps is `RiskWrite` when its method is anything
but GET or HEAD and `RiskRead` otherwise; a tool with any `shell` step is
`RiskDestructive`, so it always asks. Because `RiskDestructive` calls are
refused in a run with nobody present, shell skills are automatically kept out
of schedules and mail processing with no extra rule.

Every answer a skill produces is `Untrusted: true`: it is data fetched from
outside, never instructions.

Cache the parsed skills in the worker and rebuild when the table changes; a
simple modified-time check on each tick is enough and matches how the
connected servers' tools are refreshed.

Acceptance: with the weather skill inserted directly into the table by a test,
`teanode agent tools` lists `skill__weather__get_weather` under the `skills`
family.

### Milestone 5: installing, from the command line and the API

Add storage methods in `internal/db/database_skill.go`
(`ListAgentSkills`, `GetAgentSkill`, `PutAgentSkill`, `DeleteAgentSkill`), the
API in `internal/api/v1api/apigraph/agent_skill.go` (`ListAgentSkills`,
`SearchAgentSkills`, `InstallAgentSkill`, `UpdateAgentSkill`,
`RemoveAgentSkill`, `SetAgentSkillEnabled`), each requiring `server:manage`
except the two that only read, which require `agent:use`.

Add `teanode agent skill list|search|install|update|remove|show` in
`internal/cmd/agent_skill.go`, following `internal/cmd/agent_memory.go` for
shape.

`install` takes a name and an optional version, verifies, stores, and prints
what it installed and which tools it brought. `update` with no name checks
every installed skill against the index and installs any newer version,
comparing versions as dotted numbers with a plain numeric comparison per part.
`remove` takes the skill's tools away.

Acceptance, and the end-to-end proof of the whole plan, on a development
server:

    $ teanode agent skill search weather
    weather  2.0.0  Weather forecast via the National Weather Service API

    $ teanode agent skill install weather
    installed weather 2.0.0, which brings 1 tool: get_weather

    $ teanode agent ask "what is the weather in Alpharetta, GA?"
    … skill__weather__get_weather
    It is 68F and partly cloudy in Alpharetta …

### Milestone 6: the dashboard, and the documentation

A Skills card on `/server/agent` beside Connected servers: what is installed
with its version, a button to check for updates, a switch per skill, and a way
to install one from the registry by name. Follow `docs/coding/frontend-design.md`,
and remember that tables stay tables on a phone.

Document the feature: a section in `docs/configuration.md` for the tool policy's
new family, a row in `docs/reference/command-line.md`, a new
`docs/subsystems/skills.md` written in the style of the eight documents already
there, and a decision record `docs/decisions/20260911-skills-are-signed-and-
run-where-they-can-do-least.md` recording the two choices this plan settles:
that a skill is trusted by a signature against an embedded key rather than by
its source, and that its shell steps run on the person's computer rather than
on the mail server.

## Surprises & Discoveries

- Observation: The registry's index is signed per entry rather than as a
  whole, so an entry can be verified without trusting the rest of the file.
  Evidence: the registry's own index-verifying script checks
  `name + "\n" + version + "\n" + url + "\n" + lowercase(sha256)` per entry.

- Observation: The real skill format carries four things this plan did not
  describe when it was written, all of them in use by the five skills the
  registry publishes today. They are now implemented and covered by tests.
  Evidence: `internal/skills/testdata/unifi-protect.md` uses every one.
  They are: `secrets`, a list of values the skill needs and does not carry,
  reached as `{{secret:KEY}}`; `authenticationProfiles`, named ways of
  authenticating that several steps share, referred to by `auth: <name>` on
  a step; `actionField` with `actions`, which is one tool routing on one of
  its own parameters to a list of steps per value, so that six operations
  are one tool rather than six; and a filter after a bar in a reference,
  `{{enabled|json}}`, which writes the value as JSON rather than as text so
  that a boolean lands in a body unquoted. `json` is the only filter.

- Observation: A `Tool` cannot embed a `Step` inline in YAML: they share
  `name`, `type`, `timeout` and `command`, and `gopkg.in/yaml.v3` panics
  with "duplicated key 'name' in struct" rather than returning an error.
  The request fields are written out on `Tool` instead, and `(*Tool).
  request()` reads an http tool as the one step it is.
  Evidence: the panic, before the fix, in `TestTheRealSkillsParse`.

- Observation: All five skills the registry publishes today verify against
  the key embedded in this server, and their files hash to what was signed.
  Evidence: a throwaway program over the real index printed `ok` for git
  1.0.0, weather 2.0.0, dictionary 1.0.0, unifi-protect 1.1.0 and news
  1.0.0.

## Decision Log

- Decision: A skill's shell steps run on the person's attached computer, never
  on this server.
  Rationale: A skill is downloaded from the internet and this is a mail
  server. Even with a signature, a skill that ran commands here would make the
  mail server the thing a compromised registry reaches. On the attached
  computer the person confirms each call, the blast radius is their own
  machine, and it matches where `claude_code` and `codex` already run. The
  cost, accepted: a shell skill does nothing in a headless run.
  Date/Author: 2026-09-11, agreed with the operator.

- Decision: An operator installs a skill and it belongs to the whole server.
  Rationale: Installing a skill adds tools to everyone's agent, which is the
  same kind of act as declaring a connected server, and that is already
  `server:manage`. It gives one list to audit. Per-person installation would
  have every person separately deciding to trust a registry, with nothing an
  operator could review.
  Date/Author: 2026-09-11, agreed with the operator.

- Decision: The key committed at
  `internal/skills/keys/teanode-skills-ed25519-public.pem` is the one the
  registry published on 2026-09-11, whose file hashes to
  798d0b1e7726a1cb1432ff812092c6fc8e527590afd103c448308de669f426fa. A later
  reader comparing that hash can tell whether the key was ever changed.
  Rationale: A pinned key is only a pin if what it was pinned to is
  written down.
  Date/Author: 2026-09-11.

- Decision: The registry's public key is embedded in the binary, not fetched.
  Rationale: A key fetched from the same host as the index it vouches for
  proves nothing; whoever can serve one can serve the other.
  Date/Author: 2026-09-11.

- Decision: Template references are checked when a skill is parsed, not when it
  runs.
  Rationale: A reference to a step that does not exist would otherwise become
  an empty string in a URL, and a skill that quietly fetches the wrong address
  is worse than one that refuses to install.
  Date/Author: 2026-09-11.
