# Show mail as conversations

This ExecPlan is a living document. The sections `Progress`, `Surprises &
Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to
date as work proceeds. It follows the requirements in `~/.claude/PLAN.md`.

## Purpose / Big Picture

Today the mailbox lists one row per message and opens one message at a time.
A conversation of six messages is six rows, and answering one takes you off to
a separate page. After this change, the mailbox lists one row per
conversation; opening any message in it shows the whole conversation, newest
message first, with messages you have already read collapsed to a line and
expandable; and you reply, reply to everyone, or forward from inside the
conversation, with the box you type in at the top where the newest message is.
Messages of the conversation that live in other folders — most importantly
your own replies, which are in Sent — appear in it too.

You can see it working like this: open `https://mail.teanode.com/mailbox`,
find a message somebody has answered, and click it. The reading pane shows
the newest message expanded, the older ones as one-line summaries you can
click open, and a Reply button that opens a composer above the newest message
rather than navigating away. Send the reply, and it appears at the top of the
same conversation without leaving the page.

## Surprises & Discoveries

- Observation: `db.ItemOptions.ThreadID` already exists and already produces
  the right SQL, and had no caller anywhere in the repository.
  Evidence: `internal/db/database_mailbox.go:123` declares it,
  `internal/db/database_mailbox.go:851` uses it, and a search across
  `internal/` finds nothing that sets it.

- Observation: only externally received mail had a thread id. Everything the
  server itself wrote — a message you sent, a draft, an auto-reply, a bounce,
  a message appended over IMAP — was stored with `thread_id = ''`.
  Evidence: `internal/mx/exchange_outgoing.go` built `models.Mail{...}` with
  no `ThreadID` field, while `internal/mx/exchange_incoming.go:61` sets one.
  Consequence: without the fix in this plan, a conversation would show the
  other person's messages and never your answers.

- Observation: a message between two mailboxes on this server is one row, not
  two. The outgoing path files the sender's row in Sent and delivers the same
  row to the recipient rather than re-injecting it.
  Evidence: `internal/mx/exchange_outgoing.go:274-278`.
  Consequence: giving outgoing mail a thread id fixes both ends at once.

## Decision Log

- Decision: a conversation is computed from `mail.thread_id` at query time.
  There is no `thread` table and no `thread_id` column on `mailbox_item`.
  Rationale: the derivation already exists and is already correct; a table
  would need backfilling, and a denormalised column on the item would have to
  be kept in step every time a message moves folder.
  Date/Author: 2026-09-08, this change.

- Decision: the folder list groups by conversation *within the folder*. A
  conversation appears in a folder when any of its messages is in that folder,
  and the row shows the newest of its messages that are in that folder.
  Rationale: a folder list has to stay a folder list. If the row showed the
  newest message anywhere, Archive would list rows whose visible message is
  not in Archive, and moving a message would silently change other folders.
  Date/Author: 2026-09-08, this change.

- Decision: the conversation *view* spans the whole mailbox, every folder.
  Rationale: this is what was asked for, and it is what makes your own replies
  appear: they are in Sent, and the conversation is being read from the Inbox.
  Date/Author: 2026-09-08, this change.

- Decision: the URL does not change. `/mailbox/:folderId/:itemId` still opens
  a message; it now shows that message's conversation with that message
  expanded. Rationale: every existing link keeps working, including the ones
  in this repository's own documentation and in mail notifications.
  Date/Author: 2026-09-08, this change.

- Decision: the message a person types into is the compose page's own form,
  lifted into a component, not a second smaller editor.
  Rationale: two composers drift. `docs/coding/frontend-design.md` says to
  reach for the shared component; a reply box that could not add an
  attachment would be the first thing anybody complained about.
  Date/Author: 2026-09-08, this change.

## Outcomes & Retrospective

Everything the plan set out to do is done and deployed, bar the code review.
What is worth carrying forward:

The data was the hard part, not the display. Two thirds of the work was
making every stored message belong to a conversation, and the bug that cost
the most time was the quiet one: a message stored with an empty thread id is
not a message without a conversation, it is a message in the conversation
whose id is the empty string, so every such message grouped into one row. The
fix — assign the id where the row is created, in `CreateMails`, rather than at
each of the six callers — is smaller than the four separate fixes it replaced.

The composer went in more easily than expected. It was already one `<form>`
with no route-specific behavior inside it beyond reading the address bar, so
lifting it into a component took one edit and left the page a wrapper.

What is not done, and worth knowing:

A conversation is capped at 200 messages. Past that the newest 200 are shown
and the header says so, but the beginning of a very long conversation is not
reachable from it.

The list pages by offset rather than by cursor, since a conversation has no
UID to page from, so a message arriving between pages shifts the rest down
one; the overlap is dropped rather than shown twice.

A message that links two conversations already stored does not merge them:
`FindThreadID` takes the first id it recognizes. Merging would mean rewriting
every message of one conversation.

`FindThreadID` looks up a Message-ID across the whole server, not within the
mailbox the message is being stored for. Nothing leaks — a conversation is
only ever listed from one mailbox's own items — but somebody who knows the
Message-ID of a message you received can send you one that joins that
conversation, which reads as more trustworthy than a message on its own. It
is worth scoping the lookup to the recipient's domain.

Turning a rule on and off from the list, and marking a conversation read,
apply to the messages in the folder being looked at. In Starred and in a
search across the mailbox there is no folder, so they apply to the one
message the row shows — deliberately, because a starred conversation's
messages are spread over Sent, Drafts and Trash, and archiving from a starred
row should not archive an unsent draft.

## Context and Orientation

TeaNode is a mail server with a web dashboard. The parts that matter here:

`internal/models/mail.go` defines `Mail`, one stored message. Its `ThreadID`
field is the id of the message that started the conversation — the first
message's own id. `internal/models/mailbox.go` defines `MailboxItem`, which is
a message *in a folder*: the same message in three folders is one `Mail` row
and three `MailboxItem` rows. An item carries the read and flagged state; the
message carries the sender, subject and body.

`internal/mx/exchange_incoming.go` is what happens when mail arrives.
`internal/mx/exchange_outgoing.go` is what happens when mail is submitted for
sending. `internal/mx/exchange_mailbox.go` holds `threadIDFor`, which reads
the `In-Reply-To` and `References` headers — the headers a mail program writes
to say which message it is answering — and asks the database whether it
already knows any of them.

`internal/db/database_mailbox.go` is the query layer for folders and items.
`ItemOptions` is the filter struct; `itemQuery` builds the SQL; `ListItems`
and `CountItems` run it.

`internal/api/v1api/apigraph/mailbox.go` is the GraphQL API. The schema is
generated by reflection over Go types, so adding a field to an arguments
struct adds it to the schema; the field name comes from the `json` tag, and a
pointer field or a `graphapi:"nullable"` tag makes it optional.

`web/src/pages/mailbox.tsx` is the three-pane mailbox: rail, list, reader.
`web/src/pages/mailboxCompose.tsx` is the compose page.
`web/src/pages/mailDetail.tsx` exports `MessageContent`, the component that
renders one message's body, which the reader already uses.

## Plan of Work

### Milestone 1: every message the server writes belongs to a conversation

Scope: before anything can be grouped, the data has to be right. At the end
of this milestone every message stored by this server carries a thread id.

`internal/mx/exchange_outgoing.go`: compute `threadIDFor(tx,
envelope.Headers)` before building the `models.Mail`, set it, and after
`CreateMail` fall back to the message's own id when it is still empty —
exactly as `exchange_incoming.go` does. This is done.

`internal/api/v1api/apigraph/mailbox_compose.go`: a draft is a stored message
too. When a draft is a reply, it carries `In-Reply-To`, so the same call gives
it the right conversation.

`internal/imap/selected.go`: a message appended over IMAP — which is how some
mail programs save their own Sent copy — takes the same treatment.

Acceptance: send a reply from the dashboard, then in `psql` run

    SELECT "id", "thread_id", "subject" FROM "mail" ORDER BY "received_at" DESC LIMIT 5;

and see the reply's `thread_id` equal to the id of the message it answered,
rather than empty.

### Milestone 2: the database can list conversations

Scope: a folder's list becomes one row per conversation.

Add to `internal/db/database_mailbox.go` a `ThreadRow` type — the newest item
of the conversation in this folder, the number of its messages in this folder,
how many are unread, and the addresses that have taken part — and
`ListThreads(folderId string, options *ItemOptions) ([]*ThreadRow, error)`
plus `CountThreads`. The query is a `DISTINCT ON ("mail"."thread_id")` over
the same joined query `itemQuery` already builds, ordered so the newest item
of each conversation wins, wrapped in an outer query that orders the
conversations themselves.

Add a migration `internal/db/migrations/0022_mail_thread_received.sql` with
its `.reverse.sql`, creating an index on `mail(thread_id, received_at DESC)`
so that grouping does not sort the table. Read `docs/coding/database-migrations.md`
first: every migration ships a matching reverse file or the server refuses to
start.

Acceptance: `make test` passes, including a new test in
`internal/db/database_mailbox_test.go` that files three messages of one
conversation and one of another into a folder and expects `ListThreads` to
return two rows, the first being the newest message of the three.

### Milestone 3: the API can serve conversations

Scope: two new queries and one new argument.

In `internal/api/v1api/apigraph/mailbox.go`:

- `ListMailboxThreads(ctx, ListMailboxThreadsArguments) (*MailboxThreadPage,
  error)` taking the same filters as `ListMailboxItems` and returning thread
  rows.
- `GetMailboxThread(ctx, GetMailboxThreadArguments) (*MailboxThread, error)`
  taking a mailbox id and a thread id and returning every item of that
  conversation in that mailbox, newest first, whatever folder each is in,
  with each item's folder named so the reader can say "in Archive".
- `ThreadID *string` on `ListMailboxItemsArguments`, which is already
  plumbed through to the SQL.

Register any new document in `internal/client/mailbox.go` if the command line
should reach it, and remember `internal/api/v1api/apigraph/client_documents_test.go`
checks that the client's documents parse against the schema.

Acceptance: with the dev server running, a GraphQL query for
`GetMailboxThread` returns the messages of a conversation across Inbox and
Sent.

### Milestone 4: the list shows conversations

Scope: `web/src/pages/mailbox.tsx`. The list query becomes
`ListMailboxThreads`; a row shows the conversation's newest message, its
participants, and a count when it holds more than one; the row links to that
newest message's item id, so the existing URL shape is unchanged.

Acceptance: in `make dev-frontend`, a folder holding a conversation of three
messages shows one row reading "3".

### Milestone 5: the reader shows the conversation

Scope: `web/src/pages/mailbox.tsx`'s `Reader`, and a new component for one
message of a conversation. On opening an item, fetch its conversation, render
the messages newest first, expand the newest and anything unread and the item
that was clicked, collapse the rest to sender, date and the first line, and
expand one on click. Mark a message read when it is expanded.

Acceptance: opening a conversation of five messages of which four are read
shows one open message and four lines; clicking a line opens it in place.

### Milestone 6: replying happens in the conversation

Scope: lift the compose form out of `web/src/pages/mailboxCompose.tsx` into a
component that the page and the conversation both use, and put Reply, Reply to
all and Forward buttons on the conversation that open it above the newest
message. Sending refreshes the conversation rather than navigating.

Acceptance: reply to a conversation without the URL changing, and see the
reply appear at the top of it.

### Milestone 7: prove it

Deploy to root@server with the project's usual incantation — `make docker
DOCKER_TAG=teanode:mailboxes`, `docker save | ssh root@server docker load`,
`docker compose up -d --force-recreate teanode` in `/opt/teanode` — and check
in Chrome at 1440px and at 390px. Then read the whole diff for defects and fix
what it finds.
